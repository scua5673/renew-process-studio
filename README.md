## 2.877 작전판 한글 Enter 입력

## 2.876 조별 일정과 팀 설정 저장

주간 경기 상대 팀명은 입력값으로 즉시 저장합니다. 조별 훈련/OFF는 날짜별 override로 보존하며 다른 조의 세션을 삭제하지 않습니다. 팀 브랜딩은 최신 문서의 해당 필드만 수정하고 일반 선수단 저장은 최신 브랜딩을 유지합니다. 플레이북 비동기 갱신은 편집 중인 입력을 교체하지 않으며 개인 게임모델도 기존 기기 저장본을 먼저 읽습니다.

## 2.875 장비별 입체 형태

입체 보기의 장비 15종(골대 방향별 종류 포함)을 개별 SVG 입체 형상으로 표시합니다. 기둥·그물·지지대·원뿔·테두리에 실제 높이 좌표를 사용하며 회전 시 다시 투영합니다. 드래그 중에는 형상을 다시 만들지 않습니다. 평면 보기와 이미지 내보내기는 보존한 원래 도형을 사용합니다.

## 2.874 평면·입체 선수·공·장비 이동

평면에서도 드래그 입력을 프레임당 마지막 좌표로 모아 SVG 좌표 읽기와 반복 그리기를 줄입니다. 선수·공·전체 장비가 같은 경로를 사용하며 종료/취소 시 마지막 입력을 즉시 반영합니다. 두 보기와 가로·세로, 세 화면 크기에서 장비 종류별 이동·좌표·실행 취소를 검증합니다. 보드는 저장 버튼으로 저장합니다.

## 2.873 입체 토큰 드래그 성능

입체·중계캠 토큰 이동은 한 프레임의 최신 입력만 처리하고, 놓기·취소 시 남은 입력을 즉시 반영합니다. 실제 측정한 네 기준점과 운동장 크기가 같을 때만 원근 역변환 행렬을 재사용합니다. 자유선은 모든 입력점을 유지하며 단체 이동·고정·실행 취소·수동 저장 동작을 보존합니다.

다른 탭이 공유 캐시 표시를 먼저 지워도 현재 탭의 대기 화면과 타이머는 정상적으로 정리합니다. 전체 가리개는 최대 5초 뒤 수신 안내로 전환하며, 재시도에도 같은 시간 제한을 적용합니다. 계정·팀 잠금, 자료별 서버 확인, 미전송 편집은 변경하지 않습니다.

## 2.871 관리자 오류 조회와 저장소 연결 복구

오류 목록은 서버의 한 번 조회 제한을 넘어 페이지별로 읽고, 조회 중 기간·계정 변경을 안전하게 처리합니다. 사본 충돌·작업 변경·서버 확인 대기를 구분해 표시합니다. 닫힌 IndexedDB 연결은 실제 트랜잭션이 시작되기 전에만 다시 열며, 확정된 동기화 기준본으로 확인되는 사본은 원본을 보존한 채 사용합니다. 비동기 오류에는 민감한 URL을 제외한 발생 파일·줄 정보를 남깁니다.

## 2.870 태블릿 편집과 게임모델 입력 안정화

태블릿의 선수 배치 드래그가 화면 스크롤로 바뀌지 않도록 하고, 짧은 탭 선택과 가로 화면의 선택 메뉴 스크롤을 지원합니다. 게임모델 저장 확인은 입력칸을 다시 만들지 않으며, 늦게 도착한 과거 이벤트를 무시합니다. 화면용 사본이 없을 때는 기존 IndexedDB 자료를 소유권 확인 후 먼저 불러옵니다.

## 2.869 보드 수동 저장

일반 보드는 `저장`, 보관함에서 연 작전판은 `저장하고 나가기`를 눌러야 저장됩니다. 토큰 이동·탭 숨김·화면 전환은 저장본을 덮어쓰지 않습니다. 저장하지 않은 수정은 변경됨으로 표시하며, 새로고침 시 경고합니다. 명시적으로 저장한 자료의 오프라인 전송 재시도는 유지합니다.

## 2.868 입체 토큰과 저장 안정화

## 2.862 가용인원 통합과 미팅 PDF

참여·상태 진입로를 가용인원 화면으로 통일했습니다. 오늘은 선수단의 현재 상태를 기준으로 집계하며 과거 기록은 보존합니다. 선수·일정 변경 시 열린 화면을 갱신하고, 사유 변경도 오늘 기록과 함께 저장합니다.

미팅 편집기와 보관함에서 A4 세로·가로 PDF를 내보냅니다. 보드를 용지 영역에 맞춰 채우며 가로형에서는 보드도 가로로 그립니다. 제목·메모는 페이지당 최대 4줄이고 초과 내용은 이어서 출력합니다. 내보내기는 원본 장면과 보드 방향을 변경하지 않습니다.

## 2.857 아이패드 보드와 첫 사용 네이비 기본값

아이패드 보드 도구를 데스크톱과 같은 3행 배치로 정리하고, 보드 설정 글자를 11px로 줄였습니다. 터치 버튼은 36px 높이를 유지하며, 좁은 화면에서 넘치는 도구는 행 안에서 스크롤합니다.

잔디·딥그린·네이비·화이트·훈련 배경과 직접 색 선택을 복원했습니다. 처음 사용하는 보드는 네이비로 시작하며, 저장된 보드의 색과 이미지는 그대로 복원합니다. 계정 확인 전에는 기기 공용 배경 이미지를 적용하지 않습니다. 새 페이지와 새 보드를 만들 때는 현재 배경을 유지합니다.

## 2.856 보드 배경 선택과 관리자 화면 밀도

새 보드는 잔디로 시작하며 배경 선택은 잔디·네이비 두 가지로 정리했습니다. 새 페이지에서도 현재 배경을 유지하고, 예전 기기 색상이 나중에 덮어쓰던 경로를 제거했습니다. 저장된 보드의 기존 배경과 자료는 그대로 복원합니다.

관리자 메뉴·통계·표·목록의 여백을 줄이고, 넓은 콘텐츠 상세 화면은 그림과 설명을 나란히 배치합니다. 운영 홈은 화면 높이에 맞추고 긴 목록·상세 내용은 각 영역 안에서 스크롤합니다. 모바일의 터치 버튼과 입력 글자 크기를 유지하며, 낮은 창에서는 페이지 스크롤로 모든 내용에 접근할 수 있습니다.

## 2.855 애니메이션 장면 클릭과 보드 워터마크

보드 화면에는 실제 운동장 왼쪽 위 코너 바로 위와 오른쪽 아래 코너 바로 아래에 작은 PROCESS 워터마크를 표시합니다. 화면 크기와 운동장 방향이 바뀌면 위치를 다시 맞춥니다.

## 2.854 관리자 콘텐츠 탐색과 실제 작성자 조회

관리자 콘텐츠 화면을 왼쪽 목록과 오른쪽 큰 상세보기로 구성했습니다. 그림과 설명·코칭·메모를 함께 표시하며, 저장된 훈련·장면·작전판 페이지·애니메이션 프레임·미팅 슬라이드를 모두 탐색할 수 있습니다. 현재 필터 결과 안에서 이전·다음 콘텐츠를 열고, 팀·워크스페이스·작성자·저장 기간·폴더별로 좁혀 볼 수 있습니다. 모바일은 목록과 상세보기를 전환합니다. 본문은 선택한 항목만 조회하며, 선택·계정·화면이 바뀐 뒤 도착한 응답은 표시하지 않습니다.

새 관리자 전용 `ps_admin_content_owners` 함수는 `ps_library.owner_id`로 실제 작성자를 조회합니다. 예전 목록 RPC가 반환한 워크스페이스 소유자 이메일을 작성자로 사용하지 않습니다. 작성자 ID 자체가 없는 과거 자료는 소유자 확인 필요로 표시하며 임의로 연결하지 않습니다. 서버 적용·검증과 되돌리기 절차는 `migrations/20260917_admin_content_owners.runbook.md`에 기록했습니다.

## 2.853 스카우트 기본 정보 통합 편집과 관리자 소유자 표시

스카우트 명단의 이름을 누르면 이름·출신 팀·등번호를 한 팝업에서 함께 수정합니다. 저장 전 입력은 초안으로 유지하며, 취소 시 기존 정보를 보존합니다. 저장 중에는 중복 제출을 막고 계정·팀·권한·선수 변경을 확인합니다. 목록의 등번호는 출신 팀명과 같은 글자 형태로 표시합니다.

관리자의 콘텐츠·워크스페이스 소유자 표시는 이메일이 없으면 소유자 ID에 연결된 이름으로 보완합니다. 이름과 이메일이 모두 없으면 계정 ID를 표시하며, 식별 정보 자체가 없을 때는 소유자 확인 필요로 구분합니다. 소유자 이름과 ID도 검색할 수 있고, 서로 다른 콘텐츠 작성자와 공간 소유자를 혼동하지 않도록 합니다.

## 2.851 모바일 스카우트 출신·등번호 간격

모바일 스카우트 명단의 이름 아래에서 등번호가 출신 팀명 바로 옆에 붙습니다. 팀명을 입력할 때 표시 폭도 따라 바뀌며, 긴 팀명은 말줄임하고 등번호는 같은 줄에 유지합니다.

## 2.850 스카우팅 보드와 명단 편집 개선

스카우팅 보드 외곽을 선수단과 같은 1190:1000 비율과 최소 높이로 맞추고 스카우팅의 인원별 운동장 자동 확장을 제거합니다. 카드 폭은 146px(중간 화면 132px), 안쪽 여백 6px 7px, 선수 행 28px로 통일합니다. 카드에는 모든 선수를 유지하고 표시 위치만 보정하며 저장된 배치와 선수 자료는 바꾸지 않습니다. 좁은 보드에 모두 들어가지 않으면 보드 전체를 스크롤해 확인합니다.

후보 명단은 이름 아래에 출신 팀과 배번을 묶고, 오른쪽에 상태·평가·＋메모·화살표를 표시합니다. 이름 칸은 데스크톱 최대 160px로 줄이고 직접 편집할 수 있게 했으며, 행 끝의 화살표 버튼은 기존 프로필 편집 화면을 엽니다. 모바일에서도 한 선수의 정보와 동작을 같은 행 안에 유지합니다.

## 2.849 스카우트 정렬과 카드 높이

배번 입력칸과 머리글을 가운데 정렬하고 1~3자리 숫자에 같은 폭을 사용합니다. 평가 배지 글자도 원 안에서 가운데로 맞춥니다. 데스크톱 팀명 열은 최대 140px, 중간 폭에서는 최대 112px로 제한합니다.

보드 카드는 우리팀과 스카우트 후보를 모두 펼쳐 보여줍니다. 카드 내부 스크롤과 표시 인원 제한을 없애고 선수 수에 따라 높이가 늘어납니다. 커진 카드의 잘림과 인접 카드 겹침을 줄이도록 운동장의 표시 높이도 계산하며, 저장된 카드 위치와 선수 자료는 유지합니다.

## 2.848 스카우트 후보 한 줄 목록과 우리팀 함께 보기

스카우트 후보를 데스크톱과 모바일 모두 한 선수당 한 행으로 표시합니다. 팀·배번·이름·상태·프로필·평가·＋메모 순서로 배치합니다. 모바일에도 소속팀을 표시하며, 여러 메모와 후보 보관은 ＋메모를 눌러 펼치는 창에서 관리합니다. 메모 추가·삭제 뒤에도 창을 유지하며 새 메모에 입력 초점을 옮깁니다.

스카우팅 보드는 우리팀과 후보를 함께 보는 ‘전체’로 시작합니다. 기존 포지션 카드와 좌표를 유지하고, 같은 약어를 가진 서로 다른 포지션 카드에서도 등록된 선수가 빠지지 않도록 합니다. 선수가 많은 카드 안에서 스크롤할 수 있어 운동장이 지나치게 길어지지 않습니다.

## 2.847 경기별 GK 역할과 선발 배치 수정

경기 준비와 상대 분석에서 운동장 선수를 누르면 ‘이 경기 역할’을 기본 역할·필드·GK 중에서 고를 수 있습니다. GK 유니폼은 같은 경기의 모든 페이지와 선수 명단에 즉시 반영하며, 선수단의 기본 포지션·등번호는 유지합니다. 등번호 1번보다 명시한 역할을 우선합니다.

상대 분석의 ‘우리 11’은 경기 준비에 배치된 선발의 위치를 먼저 복사합니다(같은 페이지가 없으면 현재 준비 페이지). 준비된 배치가 없을 때는 포지션·좌우 위치·팀 구성 카드에 맞는 선수만 배치하며, 맞는 자리가 없는 선수는 명단에서 직접 배치하도록 안내합니다. 필드 선수를 임의로 빈 GK 자리에 넣지 않으며 직접 지정한 대체 GK를 우선합니다.

## 2.846 선발·리저브를 운동장 위로

경기 준비와 상대 분석의 선발·리저브를 운동장 바로 위의 가로 명단으로 표시합니다. 인원이 많으면 줄바꿈하며 빈 명단도 끌어 놓을 자리로 남깁니다. 나머지 조별 선수 명단은 왼쪽의 128~144px 열에 표시해 불필요한 가로 여백을 줄입니다. 글자 크기와 선수 데이터는 유지하며 양쪽 명단의 배치 표시, 유니폼 색, 드래그 이동과 순서 변경을 함께 처리합니다.

## 2.845 경기 준비·상대 분석의 왼쪽 명단과 자유 페이지

데스크톱과 태블릿에서 경기 준비와 상대 분석의 우리 팀 명단을 경기장 왼쪽의 세로 목록으로 배치합니다. 이름·등번호와 행 간격을 줄여 더 많은 선수를 볼 수 있습니다. 선발·리저브·선수단 조 구분과 경기장으로 끌어 놓기, 명단 간 이동을 유지하며, 세로 목록의 순서 변경도 위·아래 방향으로 맞춥니다. 좁은 휴대폰 화면에서는 명단을 경기장 위에 표시합니다.

경기 준비의 ‘＋ 페이지’는 현재 배치를 즉시 독립 복제합니다. 페이지 이름은 자유롭게 바꿀 수 있고 기존 국면 이름과 배치는 유지합니다. 자유 페이지에서도 현재 상대 분석 장면을 가져올 수 있습니다. 페이지 이름 변경·삭제 대기 중 팀·경기·페이지·권한이 바뀌면 이전 대상을 저장하지 않습니다.

## 2.842 반복 저장 충돌과 경기 확인

조건부 저장 응답이 비었을 때 실제 서버 원문과 판본을 다시 읽어, 이미 같은 내용이 저장된 경우에만 완료로 확인합니다. 이전 확인 기록에 자료가 있었는데 서버 목록에서 빠졌다면 해당 자료를 직접 조회한 뒤 동기화를 이어갑니다. 확인할 수 없는 응답이나 다른 원문은 저장 완료로 처리하지 않으며 기존 변경을 보존합니다.

경기 자료의 서버 확인이 끝났으면 다른 자료의 저장 실패 때문에 경기 화면까지 확인 대기로 돌아가지 않습니다. 계정·팀·경기 원문이 달라지거나 경기 자체의 확인이 끝나지 않은 경우에는 기존 보호를 유지합니다. 저장 충돌 안내와 개인정보 없는 진단 단계도 구분합니다. 이 변경은 재현한 저장·확인 경로의 수정이며 실제 제보자의 자료 복원을 완료했다는 뜻은 아닙니다.

## 2.841 개인 보드 복구 사본 관리

충돌 재시도마다 새 사본을 만들던 동작을 편집 창의 복구 초안 한 개를 갱신하는 방식으로 바꿉니다. 다른 창의 현재 보드는 덮지 않고, 복구 초안은 본문 비교 저장과 재조회 검증 뒤 IndexedDB에 보관합니다. 기존 계정 소유 복구 사본도 원문이 일치하는 경우에만 작은 저장소에서 정리합니다. 작은 저장소 실패만으로 전체 저장 실패를 알리지 않으며, 두 저장소 모두 실패하면 편집기는 계속 실패를 알립니다.

서버 조회 실패는 빈 보드로 처리하지 않습니다. 일반 백업에는 현재 계정의 개인 보드와 복구 사본을 포함하되, 가져오기에서 자동으로 현재 보드를 덮어쓰지는 않습니다. 복구 사본은 파일 원문을 이용한 별도 복구 대상입니다. 팀 화면의 메뉴별 파일 저장은 기존 범위를 유지합니다.

## 2.840 경기 준비 드래그·세로 경기장

저장 알림이 도착해도 잡고 있는 선수와 경기 객체를 교체하지 않습니다. 드래그를 마치고 기기 저장이 끝난 뒤 갱신하며, 취소·계정/팀/경기/국면 변경은 미리보기 위치를 저장하지 않습니다. 같은 배치의 저장 알림은 선수 선택을 유지합니다. 경기장 위 가로·세로 버튼은 표시 좌표만 바꾸므로 기존 배치·명단·공유 데이터 형식을 유지하고, 세로 화면에서도 추가·이동할 수 있습니다.

검증: `node --test tests/*.test.cjs`, `tests/browser/match-lineup.mjs` (독립된 가상 경기, Chromium/WebKit, 1280·820·390px).

## 2.839 폴더 경로 중복 사본

동일한 폴더 경로가 배열에 여러 번 들어 있어도 하나의 폴더로 봅니다. 모든 고유 경로를 보존하는 추가 관계만 수렴하며, 기기에서 사라진 기존 경로는 여전히 자동으로 복원하지 않습니다.

## 2.838 폴더 정렬과 화면 갱신

폴더 UI는 이름순으로 정렬하므로 원문 배열의 삽입 순서는 충돌로 취급하지 않습니다. 양쪽 기기 사본의 모든 이름이 서버 후보에 보존되는 추가 관계에서만 저장을 완료합니다. 폴더 화면은 동기화 반영 후 다시 읽되 계정·팀 변경, 새 편집, 대기 중 폴더 저장이 있으면 옛 읽기를 적용하지 않습니다.

## 2.837 저장 사본 불일치 진단

기기 원문을 덮지 못한 경우 원문 대신 자료 형식과 배열 항목 수만 기록합니다. 프레임 저장 이벤트가 폐기된 경우도 고정된 사유 코드로 구별합니다.

## 2.836 폴더 중간 목록 수렴

기기 IDB → 거울 → 서버 후보가 이름 중복 없는 문자열 목록이며 앞 목록의 순서를 보존하는 추가 관계일 때만, 기존 IDB CAS로 중간 거울의 반영을 완료합니다. 기기 전용 이름·순서 변경·삭제는 이 경로에서 덮지 않습니다.

## 2.835 업데이트·팀 전환 상호 배제

자동 업데이트는 활성 전환 guard와 공용 전환 잠금을 확인한 뒤 대기 저장을 마칩니다. 그 사이 계정·팀·전환 세대가 바뀌면 새로고침하지 않고 다음 안전한 때 재시도합니다. 숨은 탭에서도 이 보호를 우회하지 않습니다. 중단된 전환의 만료 표시는 부팅이 같은 배타 잠금을 얻은 뒤에만 제거하며, 이전 작업을 차단하는 전환 세대와 사용자 자료는 유지합니다.

## 2.834 IDP 읽음 기록 수렴

작성 내용이 완전히 동일하고 자동 기록 noticeSeen만 다른 private IDP는 기준본이 없어도 읽은 시각의 최댓값으로 수렴합니다. 팀 공간의 imgNotes는 기기에 보존·합치며 서버에 올리지 않습니다. 실제 작성 내용 차이·잘못된 판본·잘못된 읽음 값은 이 경로로 처리하지 않으며, 서버 CAS 확인을 받아야 대기를 해제합니다.

## 2.833 보관함 폴더 저장 완료

거울에 이미 적용할 원문이 있고 IndexedDB에는 예상했던 이전 원문이 남은 경우, 정확한 IDB 비교 저장으로 남은 반영을 완료합니다. 새로운 거울·IDB 편집은 계속 차단·보호합니다. 이 불일치 때문에 같은 보관함 충돌을 반복 처리하던 경로를 수정했습니다.

## 2.832 저장·팀 전환 안정화

전환 취소는 해당 전환의 임시 메타만 복원하며, 그 사이 완료된 저장의 확인 기록을 되돌리지 않습니다. IndexedDB 쓰기와 확인 읽기를 같은 트랜잭션에서 수행해 뒤따른 정상 저장을 검증 실패로 오인하지 않습니다.

IDP 기준본이 확인 기록과 어긋나면 계정·공간별 보관 이력에서 정확한 해시와 서버 판본이 일치하는 기준본만 읽어 병합을 재개합니다. 이력이 없거나 맞지 않으면 원문과 대기를 유지합니다. 저장 오류 로그에는 개인 식별자 없이 자료 종류를 남깁니다.

## 2.831 작업 공간 전환 저장 대기

기존 동기화 잠금과 자료 확인을 기다리는 정상 전환이 15초에 취소되던 경로의
저장 확인 상한을 40초로 조정했습니다. 전체 전환의 60초 가드, 실제 저장 결과와
대기 항목 검사, 계정·작업공간 소유자 검증은 유지합니다. 느린 확인을 네트워크
오류로 단정하던 대기 문구도 정리했습니다.

## 2.830 오른쪽 아래 저장 상태

저장 상태를 상단에서 본문 아래의 고정 높이 24px 자리로 옮깁니다. 평소에는 작은
회색 글씨로 표시하며 저장 중 깜빡임을 없앴습니다. 모바일에서는 실제로 보이는
앱·팀 메뉴 위에 배치해 보드 도구와 보관함 만들기를 가리지 않습니다. 편집기에서도
오류·별도 보관 상태의 확인 기능은 유지합니다. 데이터 저장 방식은 바꾸지 않습니다.

## 2.829 저장 표시의 화면 흔들림 수정

상단 저장 상태의 높이를 24px로 통일하고, 로그인 확인이나 편집기 진입으로
표시를 숨길 때도 자리를 유지합니다. 업데이트 배너 아래에서 저장 중·저장됨만
18px로 줄이던 중복 스타일을 제거했습니다. 저장 상태가 바뀌어도 본문 위치와
보관함·보드 프레임 크기는 유지하며, 데이터 저장 방식은 바꾸지 않습니다.

## 2.828 자동저장 기록 불일치 복구

기기에 저장한 자동저장 기준이 현재 메타데이터보다 여러 판본 앞서 있으면,
서버 조회 전 기록 검사에서 매번 중단되던 문제를 수정합니다. 과거 확인 원문은
계정·작업공간별 불변 슬롯에 정확히 보존하며 최신·직전 기록은 되감지 않습니다.
서버에서 새로 읽은 원문을 처리하는 엄격한 판본 검증과 최종 저장 확인은 유지합니다.

저장 기록 불일치와 기기 기록 보존 실패를 구분하고, 원인 미상의 오류를 인터넷
문제로 단정하던 안내도 수정합니다. 데이터 삭제·서버 스키마 변경은 없습니다.

## 2.827 코치별 개인 작업 보드

작업 중인 보드는 전용 개인 공간의 `cs_private_board_v1`에 저장합니다. 같은 계정은
팀을 바꿔도 이어서 사용하고, 보관함의 기존 공유 설정은 유지합니다. 소유자를 알 수
없는 예전 기기 보드와 팀 보드는 자동으로 가져오지 않으며 원본은 보존합니다.

계정별 기기 초안, 정확한 서버 원문·판본 비교, 늦은 응답 차단으로 계정 전환과
오프라인 편집을 보호합니다. 다른 기기의 동시 편집은 원문을 덮지 않고 기기에
보관합니다. `migrations/20260915_private_board.sql`은 두 작업 보드 키를 개인 공간
소유자에게만 허용하며, 일반 팀 자료의 과거 기록 조회에서도 같은 경계를 적용합니다.
설치 전 카탈로그 확인과 설치 후 검증은 같은 이름의 runbook을 따릅니다.

## 2.826 선수 삭제 경로와 서버 저장 확인

선수단의 포지션 팝업에서 삭제할 때도 삭제 기록과 명시적인 선수 행 삭제를
같이 저장합니다. 확인창을 기다리는 동안 계정·팀·권한·해당 선수 원문이 바뀌면
오래된 삭제 요청을 적용하지 않습니다. 미전송 삭제는 기존 보관함에서 재시도합니다.

선수 행·전체 명단·보드용 명단·공개 기준·삭제 기록은 서버가 돌려준 본문과 실제
수정 번호를 확인한 뒤에만 저장을 확정합니다. 서버 보호 규칙이 다른 내용을
유지했거나 확인 응답이 불완전하면 성공으로 처리하지 않습니다. 응답 유실 후
같은 원문을 재전송한 경우에도 실제 서버 수정 번호를 다음 비교 기준으로 씁니다.

서버 원본 통일 SQL은 `migrations/20260915_roster_canonical.*`의 **미적용 준비본**입니다.
설치·팀 활성화·앱 연결은 이번 배포에 포함되지 않습니다. 현재 서버에는 전체 명단에만
선수가 있는 이전 저장 구조도 남아 있어 일괄 전환할 수 없습니다. 준비본의 원문 백업·
불일치 차단·동시 수정·삭제·권한 검증을 로컬에서 수행하며, 실제 전환 조건은 해당
runbook에서 관리합니다. 운영 데이터의 삭제·초기화·일괄 합치기는 하지 않았습니다.

## 2.825 선수단 저장 경로 정리 — 1단계

선수단의 일반 저장을 `rosterPersist`로 모아 본문·선수 행·공개 속성·명단 사본의
완료/실패를 함께 추적합니다. 선수 행은 실제로 변경한 ID와 명시적으로 삭제한 ID만
저장합니다. 참여 메모·팀 설정만 바꿀 때는 선수 행 전체를 다시 쓰지 않습니다.
빈 이름의 신규 선수는 본문 초안으로 남기고 이름이 입력된 뒤 행으로 생성합니다.

서버에서 확인한 선수 행을 화면에 반영하는 경로는 `rosterProject`로 분리했습니다.
이 경로는 후보 문서·평가 모드·보드 슬롯을 새 편집처럼 다시 저장하지 않습니다.
읽기를 시작한 뒤 계정·팀·권한·명단·삭제 기록이 달라지면 늦은 결과를 적용하지 않습니다.

미전송 선수 변경은 `ps_roster_pending_v1:<계정>:<팀>:` 아래의 기기 보관함에 먼저
기록합니다. 원본 기준과 새 입력을 저장·재검증한 뒤 본문을 접수하며, 행 저장이
실패해도 새로고침 후 해당 변경을 표시하고 재시도합니다. 새 변경이 이전 저장의
늦은 완료 응답에 지워지지 않도록 불변 묶음과 정확한 확인 기록을 사용합니다.
선수 행의 기기 저장 확인과 서버의 저장 확인은 구분합니다. 상단의 서버 저장 상태는
기존 조건부 전송과 실제 응답 확인을 그대로 사용합니다.

이번 단계는 **클라이언트 저장 경로 정리**입니다. 기존 `scout_tool_v1` 전체 문서와
`cs_squad_v1` 호환 사본은 계속 저장하며, 선수단 원본의 서버 단일화·참여 기록의
별도 행 분리·서버 복구 이력 이관은 아직 적용하지 않았습니다. 운영 DB 스키마 변경이나
기존 명단 일괄 수정은 없습니다. 다음 전환은 원문 백업, ID·삭제 기록·내용 비교,
구버전 쓰기 차단과 읽기 전환을 갖춘 별도 단계로 진행해야 합니다.

## 2.824 사용법 탭과 웹 안내

앱 설정의 **사용법** 탭에 앱 사용법·전체 설명서·팀 운영·IDP·팀 시작·설치 안내를
모았습니다. 모든 링크는 새 탭에서 열립니다. 기존 6개 언어의 팝업 사용법은
`/guide/quick.html`로 옮겨 주소·목차를 공유하고 다시 읽을 수 있습니다.

## 2.823 선수별 누적 한 줄 목록

선수별 누적을 높이 약 45px의 한 줄 목록으로 정리했습니다. 이름·번호·포지션과 5개
누적 항목을 같은 줄에서 비교하고, 모바일의 훈련·경기 세부는 선택한 선수 이력에서 확인합니다.

## 2.822 팀 운영 안내

앱 설정 → 일반의 **팀 운영 안내** 링크가 `/guide/team.html`을 새 탭으로 엽니다.
로그인 없이 읽을 수 있는 독립 페이지에 팀 시작·멤버 권한·선수 계정 연결,
일정과 참여·경기 준비와 리뷰·IDP·팀 기준·스카우팅·공유와 저장을 안내합니다.
모바일 목차와 자주 묻는 질문을 제공하며 서비스워커의 선택 캐시에도 포함합니다.

## 2.821 참여 기록과 선수별 누적

팀 운영의 출석 탭을 참여로 변경했습니다. 날짜별 행을 선택하면 그날의 참여·쉼 명단을
확인하고 상태와 메모를 기록합니다. 선수별 누적 화면에서는 훈련·경기·쉼, 부상·재활
일수를 비교하고 각 선수의 날짜별 기록을 엽니다. 오래 같은 상태라는 자동 안내는 제거했습니다.

직접 기록은 `scout_tool_v1.meta.participationDays[date][playerId]`에 날짜별로 보관합니다.
지난 날짜 수정은 기존 상태 기간과 메모·오늘 상태를 변경하지 않습니다. 오늘 기록은
현재 선수 상태에도 적용하여 부상·재활이 복귀 전까지 주말을 포함해 이어집니다.
기록이 없는 과거 날짜는 훈련이나 휴식으로 임의 생성하지 않습니다. 이전 자료는 저장된
상태 이력과 현재 조별 일정 기준으로 집계하므로 직접 기록과 구분하여 표시합니다.

훈련·경기와 쉼은 해당 일정일 기준, 부상·재활은 달력일 기준입니다. 읽기 자체는 새
상태 이력을 저장하지 않습니다. 기존 편집 권한을 유지하고, 계정·팀·권한·같은 기록이
바뀌면 늦은 수정을 막습니다. 기기 저장 완료는 저장 큐 확인 뒤에만 표시하며 서버
저장은 공통 자동 저장 상태를 사용합니다. DB 스키마 변경은 없습니다.

## 2.817 자동 저장과 기기 간 변경 병합

서버가 확인한 원문을 계정·팀별 기준본으로 보관하고, 동시에 바뀐 자료는 항목별로
비교합니다. 서로 다른 필드와 고유 ID 항목의 변경은 합칩니다. 같은 필드 충돌이나
기준본이 없는 구버전 자료는 양쪽 원문을 기기에 검증 보관한 뒤 서버 내용을 사용합니다.
삭제된 선수의 옛 사본을 새 선수로 합치지 않습니다. 실제 서버의 조건부 저장 응답을
확인하기 전에는 저장 완료로 표시하지 않습니다.

상단에는 작은 저장 상태를 표시합니다. 일반 저장과 팀 전환에서 문서 선택 창을
자동으로 열지 않습니다. 보관 실패·권한·연결 문제는 저장 미완료로 남기며 원문을 유지합니다.
복구 사본은 앱 설정 → 데이터 → 고급 → 최근 변경 복구에서 직접 확인하고 파일로
저장합니다. 사본은 이 기기에 보관되며, 서버와 다른 기기에 자동으로 복제되지 않습니다.
계정·팀·권한이 바뀐 비동기 응답과 보관 도중 추가된 입력은 적용하지 않습니다.

## 2.816 관리자 오류 제보 접수함

관리자 페이지의 오류 제보 메뉴와 운영 홈에서 앱의 제보를 확인합니다. 목록을 열면 전체
제보가 보이며 선택한 글의 내용, 첨부 환경·로그, 대화와 답변 입력을 함께 표시합니다.
관리자가 등록한 답변은 같은 제보에 저장되어 사용자의 내 제보와 답변에서도 확인됩니다.
기존 비공개 제보 RPC와 관리자 인증을 재사용하며 추가 DB 설치는 필요하지 않습니다.
자동 수집 오류 분석은 기존 오류 메뉴에서 계속 확인합니다.

## 2.815 오류 제보·답변과 최근 업데이트 안내

앱 설정 아래의 오류 제보 메뉴에서 문제를 작성하고, 본인 제보와 운영자 답변을 확인합니다.
모바일에서는 앱 설정 → 일반 → 오류 제보에서 엽니다. 제보·답변은 작성자와 서비스 관리자만
볼 수 있고, 팀 운영진 권한만으로 다른 사람의 제보를 조회하지 못합니다.

사용 환경과 현재 실행 중 수집한 최근 오류 40개를 함께 확인·복사합니다. 제보·저장된 답변·
작성 중인 답변까지 전체 복사할 수 있으며, 로그인하지 못한 경우에도 작성과 복사는 가능합니다.
진단에는 오류 분류·코드·정적 파일 위치만 포함하며 원문 오류 메시지, 로그인 토큰, 선수 자료,
URL 쿼리와 해시는 넣지 않습니다. 계정·팀 전환 시 이전 수집 기록을 비웁니다.

제보·답변 초안은 계정별로 보관하고, 응답을 확인하지 못한 등록 요청은 동일한 UUID와 내용으로
재시도합니다. 서버에서 해당 ID의 저장을 확인하기 전에는 등록 완료로 표시하지 않습니다.
기기 저장이 실패한 초안은 같은 실행 중 메모리에 유지하며 새로고침 전에 보호합니다.

최근 업데이트는 화면 상단에 표시합니다. 일주일간 안 보기는 현재 안내 내용에만 적용되며,
새로운 내용이 추가되거나 변경되면 7일 이내에도 다시 나타납니다. 기존 안전한 앱 업데이트와
지연 저장 완료 확인은 유지합니다.

서버 기능은 `migrations/20260915_support_reports.runbook.md`의 사전 확인·설치·검증 순서로
적용한 뒤 이 클라이언트와 함께 배포해야 합니다. SQL이 없는 서버에서는 접수 불가를 안내하고
작성 내용·로그 복사를 유지합니다. 로컬 검증은 운영 DB 적용을 의미하지 않습니다.

### 저장 선택과 복구 도구 분리

상단과 설정의 저장 안내는 현재 선택이 필요한 변경만 보여 줍니다. 과거 충돌 사본이
남아 있다는 이유로 일반 동기화가 다시 선택 화면을 열지 않습니다. 지난 판본, 서버 점검,
이전 사본 내보내기는 앱 설정 → 데이터 → 고급 → 복구 도구에서 직접 엽니다.
실제 선수 삭제 보류는 일반 선택 화면에도 남기며, 원본 보관과 명시적 선택 절차를 유지합니다.

## 2.813 로그인 복귀와 작전판 고정색

이미 열린 앱 문서가 새 로그인 응답을 받으면 토큰 저장과 주소 정리를 확인하고,
새 문서에서 계정과 자료를 준비합니다. 이전 로그인에서 시작한 준비 작업은 새 로그인에
적용하지 않습니다. 불완전한 응답이나 기기 저장 실패는 안내하며, 다시 로그인하거나
기존 계정으로 명시적으로 돌아갈 수 있습니다. 로그인 만료 배너의 다시 로그인 버튼을
눌렀을 때 계정 메뉴가 즉시 닫히던 문제도 수정했습니다.

작전판 색상 메뉴에 회색과 ‘현재 색 고정’, ‘편집’을 추가했습니다. 원하는 색은 최대
6개까지 이 브라우저에 기억합니다. 같은 계정으로 다시 접속하면 유지하며, 다른 계정으로
바꾸면 기존 기기 자료 정리 정책을 따릅니다. 직접 고른 새 색은 빈자리가 있을 때 기억하고,
기존 고정색을 자동으로 밀어내지 않습니다. 여러 선수의 색 변경과 실행 취소도 유지합니다.

## 2.812 계정·팀 전환 중 지연 작업의 적용 방지

로그인 갱신과 로그아웃은 시작한 로그인에만 적용합니다. 팀 생성·합류·초대·나가기와
권한 관리도 요청과 응답, 확인창 실행 때 계정·팀을 확인하며 정상적인 토큰 갱신은 허용합니다.
권한의 늦은 읽기가 새 계정 또는 이후에 변경된 권한을 되돌리지 않도록 합니다.

팀 전환은 저장 대기부터 실제 IndexedDB 삭제까지 소유자를 확인합니다. 실패하거나 시간이
초과된 이전 전환이 새로 받은 자료를 지우거나 새 계정을 이전 팀에 연결하지 않습니다.
사진·초기 저장소 이관과 일정 읽기도 소유자와 원문이 그대로일 때만 반영합니다.
지연 저장·재시도·저장소 정리도 시작한 계정과 팀에서만 완료하며, 정상 팀 전환은
진행 중인 저장을 먼저 마칩니다. 읽기 전용 진입의 화면 준비는 자동 저장을 만들지 않습니다.

새 기기에서 선수 명단을 받으면 안전 저장소와 화면 사본을 함께 준비합니다. 이미 받은
명단의 화면 사본이 빠져 있어도 다시 채우며, 첫 확인이 끝나기 전에는 빈 초기 명단을
저장하거나 자동 정규화하지 않습니다. 기존 기준본이 있는 미전송 편집과 오프라인 명단은
계속 열며, 서버에 명단이 없는 새 팀은 확인 후 정상적으로 명단을 만들 수 있습니다.

개인·공개 IDP의 전송 확인은 화면과 동기화가 사용하는 원문을 읽습니다. 예전 IndexedDB
사본 때문에 이미 저장한 기록이 계속 대기로 남거나 새 입력을 저장 완료로 오인하지 않습니다.

계정 변경 중 숨은 작전판의 높이 보정이 반복되던 문제도 수정합니다. 유효한 화면 크기를
확인한 뒤 여백을 계산하고, 작전판을 다시 열면 실제 크기에 맞춥니다.

## 2.811 선수 삭제 저장과 이미지 복원 안정화

우리 선수 삭제는 선수 명단과 삭제 기록만 저장합니다. 수정하지 않은 스카우팅 후보를
다시 저장하지 않아, 후보의 동시 저장 확인과 충돌하는 경로를 제거했습니다.

저장된 JSON의 필드 순서나 공백이 달라져도 팀 엠블럼과 일정 그림의 참조를
같은 객체에서 찾아 복원합니다. 이미지 외의 원문과 아직 받지 못한 참조는 보존합니다.

## 2.810 선수 삭제와 계정 연결 변경의 정확한 반영

선수 삭제는 기기의 색인에 해당 ID가 없어도, 사용자가 삭제를 확인한 선수의 서버 행에
삭제 기록을 반영합니다. 명단은 화면용 저장소와 안전 저장소에 함께 기록하고
실제 저장 완료를 검증합니다. 다른 계정·팀으로 바뀌거나 원문이 달라지면 중단합니다.

권한 관리에서 선수 연결만 바꾸면 그 연결만 저장합니다. 다른 멤버의 역할·편집 권한과
설정은 보존하고, 같은 필드가 다른 기기에서 바뀌었으면 다시 확인하도록 안내합니다.

## 2.809 오래된 선수 행의 재등록 방지

기기에만 남은 옛 선수 행은 현재 명단에 자동 추가하거나 서버에 신규 등록하지 않습니다.
현재 계정·팀에서 서버 판본을 확인한 행만 명단에 반영하며, 직접 추가한 선수와
다른 기기에서 등록한 선수는 정상 동기화합니다. 선수 삭제 기록은 명단 표시와 서버 전송
양쪽에 적용하고, 충돌 검토 중인 원문은 자동 명단 저장으로 덮어쓰지 않습니다.

이미 늘어난 명단은 자동으로 삭제하거나 이름으로 합치지 않습니다. 저장 이력과 정확한
선수 식별번호를 비교하고 원문을 보존한 뒤 별도로 복구해야 합니다.
자료 확인의 지난 판본에서 ‘명단 비교·백업 보기’를 열면 공통·추가·누락 ID와 현재 원문을
읽기 전용으로 확인할 수 있습니다. 계정·팀·조회 권한이 바뀌면 비교 내용을 비웁니다.

## 2.808 조용한 접속과 로그인·자료 보호

팀에 들어갈 때 이름 입력창을 자동으로 열지 않습니다. 서버에 저장된 내 이름은 조용히 복원하며,
이름 설정·변경은 계정 메뉴에서 직접 엽니다. 팀 생성·초대 코드 합류 중 이름 입력은 유지합니다.
작전판 첫 진입의 설정·팀 색상·과거 업데이트 안내와 과거 팀 편집 정책 안내의 자동 표시를 제거했습니다.
로그인 확인을 기다리는 보관함의 자동 갱신은 조용히 대기하며, 실제 저장 버튼의 로그인 안내는 유지합니다.
로그인·자료 소유자 확인과 저장 실패·복구 보호는 유지합니다.

로그인 확인 중 계정이 바뀌면 이전 응답이 새 계정의 기기 자료를 지우지 못하게 막습니다.
선수 삭제는 계정·팀과 원본을 재확인하고 기기 저장 완료를 검증합니다.
선수 정보 충돌은 내 원본을 보존한 채 자료 확인에서 선택하며, 저장하지 못한 복구 사본을
저장했다고 안내하지 않습니다. 관리자 로그아웃도 앱의 미전송 자료 확인 절차를 거칩니다.

## IDP의 첫 행동과 기록 근거

목표의 **내 방향 쓰기**에서 되고 싶은 선수와 이번에 키울 행동 하나를 적고
**저장하고 오늘 기록하기**로 이어간다. 이유와 추가 행동은 선택 사항이며 기존 행동·집중 ID는 유지한다.
목표 내용이 아직 없으면 목표 사다리·장단점·내 무기는 **목표 더 살펴보기**에서 펼친다.

오늘은 기존 주간 초점·12주 문장을 먼저 사용하고, 없으면 내 방향의 집중 행동을 보여준다.
행동 시도와 한 마디를 한곳에 두며, 참여·강도·컨디션·수면 기록은 유지한다.
시도한 문장이 내 방향의 행동과 같고 기존 연결이 없을 때만 당시 행동의 ID·문장·판본을 함께 저장한다.
시도 응답을 바꿔도 기존 장면의 연결은 자동으로 지우지 않는다. 필요하면 **행동 연결 해제**를 누른다.

과거 일간·주간 및 주간 회고에서 저장된 행동과 한 마디를 다시 읽을 수 있다.
당시 방향은 정확히 같은 판본이 남아 있을 때만 표시하며 현재 문장으로 과거를 바꾸지 않는다.
내 방향 저장 충돌은 작성 중인 문장을 기기 초안에 보관하고, 최신 내용과 비교해 사용할 내용을 고를 수 있다.

```bash
node tests/browser/idp-start.mjs
```

## 훈련 날짜의 개인 초점과 자기보고 강도

세션 채우기와 기존 세션 상세에서 **개인 초점 참고**를 펼치면 선택한 훈련 날짜의 주간 초점과
그 날짜까지 작성된 최신 코치 리뷰를 따로 읽는다. `focusByWk[월요일]`을 먼저 사용하고,
이전 형식의 `focus`는 주가 정확히 같을 때만 사용한다. 코치 리뷰는 참고 기록이며 그 훈련에서
실제로 적용했다는 뜻은 아니다. 현재 목표로 과거 초점을 보완하거나 자동 저장하지 않는다.

대상은 저장된 세션 조 → 하루 조 → 팀 공통 순서와 현재 선수단의 계정 연결을 따른다.
기존 훈련의 빈 `grp` 배열도 하루 조를 상속한다. 이는 경기 리뷰 과제의 `grp: []` 규칙과 다르다.
후보·삭제 선수와 모호한 중복 연결은 제외하며, 실제 출석·과거 조 편성은 추정하지 않는다.
없는 IDP 캐시는 아직 확인하지 못한 자료로 표시한다.

그래프의 계획 부하는 기존 전체 일정의 `RPE × 계획 분`을 유지한다. **선수 자기보고 강도**는
해당 날짜 일지의 유효한 RPE 1~10 평균과 응답 수 / 현재 연결 선수 수를 별도 카드로 표시한다.
조 선택은 이 카드만 바꾸며 일정이나 개인 문서에 쓰지 않는다. 휴식·부상중, 0·범위 밖 값은
평균에 넣지 않고 미응답은 0으로 계산하지 않는다. 실제 참여 시간이 없으므로 계획 분을 곱하거나
계획 부하와의 차이율을 계산하지 않는다. PDF는 계획 자료만 내보낸다.

두 참고 화면은 자료가 준비된 팀 공간의 관리자·운영진·스태프에게만 열리며 계정·팀·권한 변경이나
자료 잠금 때 기존 참고 내용을 지운다. 스태프의 조 필터는 읽기 전용으로 사용할 수 있다.


## 2.750 일정 준비 확인과 IDP 편집 복구

경기에서 훈련 과제를 열기 전에 일정의 서버 확인본, IndexedDB와 화면 사본이 일치했는지
현재 계정·팀·전환 시점을 함께 확인한다. 서버에서 없음을 확인한 일정만 새 일정으로 다루며,
권한 거절·저장 실패·원문 누락은 빈 일정으로 간주하지 않는다. 입력 중인 일정이나 경기 리뷰는
준비 상태 알림 때문에 교체하지 않는다.
훈련 연결 폼은 화면에 고정해 배경 스크롤에 따라 잘리지 않으며, 작은 화면에서도 닫기 버튼에 접근할 수 있다.

IDP 편집 초안은 계정·팀·탭별 `ps_idp_edit_recovery_v1:` 기기 키에 보관한다.
서버 동기화 대상에 넣지 않는다. 최신 문서와 겹치지 않는 변경을 구분하고, 같은 항목은 사용자가
선택한 뒤 적용한다. 비교 뒤 최신 내용이 다시 바뀌면 재확인을 요청한다. 날짜별 일지·배열·내 방향의
기록 구조를 보존하며, 정상 저장 또는 명시적인 취소 뒤에만 해당 초안을 정리한다.
새로고침 뒤 같은 탭의 미완료 초안을 찾을 수 있고 최근 해결 기록 한 건을 보관한다.
브라우저 기기 저장이 막히면 복구를 보장하는 대신 화면을 닫기 전에 저장하도록 안내한다.

```bash
node tests/browser/idp-recovery.mjs
PS_BROWSER_ENGINE=webkit node tests/browser/idp-recovery.mjs
PS_BROWSER_ENGINE=webkit node tests/browser/idp-start.mjs
PS_BROWSER_ENGINE=webkit node tests/browser/review-training.mjs
PS_BROWSER_ENGINE=webkit node tests/browser/storage-safety.mjs
```

위 네 브라우저 검사는 `PS_BROWSER_ENGINE=chromium|webkit`을 지원한다(기본 Chromium).
WebKit 엔진은 Playwright 설치 환경에 별도 준비해야 한다. 모바일 크기의 Mac WebKit 검증은
실제 iPhone Safari·홈 화면 설치·키보드·서버 권한 검증을 대체하지 않는다.
Node 회귀에는 독립 로컬 상태 두 벌과 가상 서버에서 오프라인 수정·재연결·응답 유실 뒤 재시도·
오래된 충돌 선택을 실행하는 검사가 포함된다. 실제 두 기기 검증 결과와 구분한다.

## 2.787 남아 있던 자동 값 초안은 열 때 지운다

2.786 을 실계정에 올려도 예전 판이 남긴 초안(noticeSeen 하나)은 다음 save() 가 돌기 전까지 띠로 남았다. 복구 기록을 읽을 때 pending 이 전부 AUTO 값이면 기기 안 복구 키에서 pending 을 지우고 띠를 띄우지 않는다. IDP 문서는 손대지 않는다.

## 2.786 IDP 복구 띠 — 자동 값은 초안이 아니다

사용자 «(아직 저장하지 못한 입력이 있어요) 이거 왜 뜨는 거야?». 실계정 기기의 복구 기록을 읽으니 pending 은 `noticeSeen`(공지 읽은 시각) 하나였다(2026-09-13 11:50:59). save() 는 먼저 초안을 잡고 250ms 뒤에 쓰는데, 그 사이 다른 기기·서버에서 문서가 바뀌면(`current!==_docSeenRaw` → idpRecoveryConflict) 쓰기를 건너뛰고 초안만 남는다 — 공지를 읽을 때 앱이 스스로 적는 시각 하나가 «입력»으로 남아 띠가 떴다. 이제 복구 diff 가 `noticeSeen` 을 건너뛰고(AUTO 목록), 공지 읽음 기록은 편집 기준본(_idpEditBase)에도 같이 적는다. 남아 있던 초안은 다음 save() 에서 diff 가 비어 스스로 지워진다. 진짜 입력(한 마디·초점 칩 등)의 복구는 그대로.

## 2.784 작전판 마커 칩 색

## 2.779 IDP 부팅 층은 'home'

2.778 을 실계정에서 재니 잘못된 화면은 사라졌지만 가리개가 ~1초 남았다 — openPersonal 은 layer 'home' 을 보내고 idp 는 이를 nextLayer 'home' 으로 받는데(주석과 달리 'cal' 로 바꾸지 않는다), 부팅을 'cal' 로 맞춰 상태가 달라 매번 다시 그리고 ack 가 render 뒤에 왔다. 부팅 층을 'home' 으로, 2.260 폰 규칙 뒤에 둔다. 이제 신호가 오면 같은 상태라 즉시 ack → 가리개가 수십 ms 안에 풀린다.

## 2.778 IDP 여는 순간의 번쩍임 — 부팅 화면을 문과 맞춤

2.777 을 실계정에서 재니 가리개 클래스는 붙는데 CSS 가 폰 세로 `@media` 블록 안에 들어가 데스크톱에서 안 먹었고, 프레임이 «프로필» 로 미리 그려져 있다가 openPersonal 을 받고 **~0.9초 다시 그리는** 사이가 곧 번쩍임이었다. 두 가지: ① 가리개 CSS 를 최상위로(`!important`). ② 셸 안(data-shell)에서는 idp 부팅 상태를 openPersonal 이 만드는 상태(curL='cal', personalOnly=true)와 똑같이 맞춰, 신호가 오면 같은 상태라 다시 그리지 않고 ack 만 보낸다. 팀에서 여는 선수단은 openSquad 가 personalOnly 를 끈다. 단독 실행은 그대로(첫 화면 프로필).

## 2.777 IDP 여는 순간의 번쩍임 — 셸 쪽 가리개

2.776 을 실계정에서 다시 재니 44ms 번쩍임이 남았다. 셸이 부팅 때 IDP 프레임을 미리 로드해 두어 프레임은 이미 «프로필» 로 그려져 있고, 누르면 셸이 프레임을 먼저 보여 준 뒤 신호를 보낸다 — idp 안의 가리개(2.776)는 첫 부팅에만 듣는다. 이제 셸이 **프레임이 새로 보이는 전환**(개인 IDP 는 `_psVisBefore!==fIdp`, 선수단은 눌리기 전 프레임이 안 보였을 때)에서 `#fIdp.ps-routing{visibility:hidden}` 을 걸고, idpPersonalAck·squadAck(문이 정해져 render 끝)에서 푼다. 재시도 소진·900ms 안전망에서도 푼다. 같은 프레임 재클릭은 가리지 않는다.

## 2.776 IDP 여는 순간의 번쩍임

사용자 «IDP 들어가면 처음에 다른 페이지가 떴다가 순간적으로 바뀌는 거 같아». 실계정 탭에서 40ms 간격으로 재니 프레임이 619ms 에 «프로필·평가» 로 먼저 그려지고 728ms 에 셸의 openPersonal 을 받아 일지로 바뀌었다(약 110ms). 2.101 의 `data-boot` 가리개는 탭 줄·액션만 가리고 본문(.stage)은 안 가렸으며, idp 자체의 첫 render 가 가리개를 바로 풀었다. 이제 셸 안에서는 본문까지 가리고, 셸의 문 신호(openPersonal·openSquad·openPlayer)를 받은 render 에서만 푼다(`window.__psRouted`). 신호가 안 오면 기존 1.2초 타이머가 푼다. 단독 실행은 변화 없음.

팀 구성 SVG(명단 출력·매치데이 문서의 운동장)와 경기 명단 화면(mlbRender)이 포메이션 표 대신 카드 11장을 자리로 그린다(세로 좌표계로 환산).
문서 범례는 «선발 (팀 구성 카드 자리 기준)». 새 경기의 포메이션 글자는 카드에서 읽은 모양(예: 4-1-2-3)으로 시작한다. 카드가 없는 팀은 예전 그대로.
«포지션 카드 열한 장» 세 판(2.759~2.761)이 이것으로 끝난다. 남은 것: 폰의 명단 그룹용 포메이션 셀렉트(#tmForm)는 그대로 — 카드 11장을 폰 명단 그룹에도 쓰려면 다음 판.

## 2.760 자리의 원본을 카드로

팀 구성이 저장될 때마다 카드 11장의 포지션·좌표를 `meta.tbSlots` 로 내보낸다. 경기 준비 «선발 배치», 상대 분석 «우리 11», 작전판 «선발 배치» 는
포메이션 표(MB2_FORMS·FORM) 대신 이 11장을 자리로 쓴다(좌표는 각 운동장 좌표계로 환산, 매칭 규칙은 2.752 그대로). 카드가 없으면 예전처럼 포메이션 표.
토스트는 «팀 구성 카드 4-2-3-1 자리에 놓았어요». 다음 판: 2.761 명단 출력·PDF 의 포메이션 글자를 카드에서 읽은 모양으로.

## 2.759 팀 구성 — 포지션 카드 열한 장

사용자 제안 «카드를 항상 11개 띄우고 포지션을 고르게 하면 포메이션을 없애도 된다». 운동장의 카드는 늘 11장(`data.meta.tbCards`, 처음엔 지금 포메이션의 자리로 만든다).
카드 머리의 포지션은 고르는 것(select)이고 자리는 끌어서 정한다(좌표 그대로). 고른 포지션이 다른 카드에 있으면 둘이 맞바꾼다.
11장에 없는 포지션의 선수는 «운동장 밖» 줄에 카드로 선다(모양엔 안 셈). 헤더의 «모양 4-2-3-1» 은 카드에서 읽은 표시일 뿐 저장하지 않는다.
포메이션 셀렉트는 운동장이 보이는 폭(≥761)에서 숨긴다 — 폰은 명단 그룹용으로 남긴다. 다음 판: 2.760 경기 준비·상대 분석·작전판 «선발 배치» 가 이 11장을 자리로.

## 2.758 들어오는 문 · 닫는 문

주간 일정·주간 카드의 경기 버튼 하나가 **지금 비어 있는 첫 걸음**을 가리킨다 — 상대 분석이 비었으면 «상대 분석 →», 채워졌으면 «경기 준비 →», 경기가 지났으면 «경기 리뷰 →»
(제안이 아니라 상태. 선수는 상대 분석을 못 보니 준비). 누르면 그 단계로 바로 열린다(step 이 일정 → 셸 → 경기 화면으로 전달).
경기 리뷰 «준비 → 실행 확인» 첫 줄에 **«결론이 맞았나»**(맞았다·반쯤·틀렸다 + 한 줄). 상대 분석 맨 위에 **«지난 상대 분석»** —
상대팀 이름이 같은 지난 경기 중 분석을 적은 가장 최근 것의 결론·맞았나·파고들 것·조심할 것이 읽기만으로 비치고, «열기 ›» 로 그 경기의 상대 분석을 연다.
설계 목업 «상대 분석에서 경기 준비까지»의 네 판(2.755~2.758)이 이것으로 끝난다.

## 2.757 보드 가져오기 · 담당 상대

경기 준비 보드 도구줄에 **«상대 분석에서»** — 같은 국면(볼 소유 시 … 세트피스)의 상대 분석 현재 프레임 상대 토큰을 이 보드의 상대 자리로 복사한다.
연결이 아니라 복사라 여기서 옮기면 여기만 바뀐다. 그 국면에 상대 배치가 없으면 안내만 한다.
선수별 경기 준비에 **담당 상대** 칩 — 상대 분석 키 선수 줄에서 하나를 고른다(개인 준비 값 `mark`, 공개 시 선수에게 그대로). 키 선수가 없으면 칩 줄이 숨는다.
다음 판: 2.758 경기 카드 버튼이 첫 빈 걸음을 가리키기 · 리뷰 «결론이 맞았나 ○/×» · «지난 상대 분석 ›».

## 2.756 상대 분석 순서

상대 분석은 국면 5줄이 문이고 보드는 근거다. 카드 순서를 01 상대가 국면마다 → 02 키 선수 → 03 장점·단점 → 04 결론 → 05 관찰 메모 → 장면(보드·트레이·프레임)으로.
국면 줄마다 «장면 ›» 가 아래 보드를 그 국면으로 열고 스크롤한다. 보드 탭 이름도 같은 말(볼 소유 시·볼 비소유 시·공격 전환·수비 전환·세트피스)로 표시한다(저장 라벨은 그대로).
보드·트레이·프레임·재생은 2.754 그대로다. 다음 판: 2.757 «상대 분석 장면 가져오기» · 선수별 «담당 상대».

## 2.755 상대 분석 → 경기 준비 이어짐

실측: 상대 분석에 적는 국면 5줄·키 선수·장단점·결론은 경기 준비·오늘·리뷰 어디에서도 읽히지 않았다. 코치는 게임플랜을 빈 칸에서 외워서 다시 썼다.
이제 경기 준비 맨 위에 **«상대에서 넘어온 것»**(결론·파고들 것·조심할 것·키 선수, 읽기만, 누르면 상대 분석으로)이 비치고,
게임플랜 각 줄 위에 상대의 짝 국면이 회색 참고 줄로 붙는다(우리 볼 소유 ↔ 상대 볼 비소유, 우리 공격 전환 ↔ 상대 수비 전환).
상대 분석의 국면 이름을 게임플랜과 같은 말로 맞췄다(공격 시 → 볼 소유 시). 저장 필드는 하나도 바꾸지 않는다. 앱은 거울이라 대신 쓰지 않는다.
설계 목업: 상대 분석에서 경기 준비까지(2026-09-13). 다음 판: 2.756 상대 분석 순서(국면 5줄이 문, 보드는 장면).

## 2.754 상대 분석에도 우리 팀 트레이

상대 분석 운동장 위에 경기 준비와 같은 «우리 팀 · 선발 · 리저브 · 조별» 트레이가 뜬다. 같은 `m.squad` 를 읽고 쓰므로
한쪽에서 선발·리저브를 바꾸면 다른 쪽도 바로 바뀐다. 칩을 끌어 상대 분석 운동장에 놓으면 현재 국면·프레임에 토큰이 서고
(경기 준비처럼 선발로 표시), 배치된 선수는 ✓ 로 보인다. 트레이 코드는 하나(`mb2RenderTray(m,target)`)이고 대상만 다르다(`MB2_TARGETS`).
폰(767px 이하)의 경기 준비 운동장 숨김 규칙은 그대로 경기 준비에만 적용된다.

## 2.753 경기 준비 «선발 배치»

경기 준비 도구줄에 «선발 배치» 를 되살렸다(2.001 에서 숨긴 «우리 11»). 규칙은 2.752 의 상대 분석과 같다 —
선발 명단만, 이 경기의 포메이션, 포지션 → 자리(정확 → 세부·기본 → 라인 → 빈 자리). 두 화면이 한 함수(`matchStartersToSlots`)를 쓴다.
트레이에서 하나씩 끌어 놓는 방식은 그대로이고, 배치 뒤 트레이의 «배치됨» 표시와 개수가 맞춰진다. 선발이 없으면 안내만 한다.

## 2.752 코치 피드백 셋 — 상대 분석 선발, 세부 포지션, 애니메이션 장면 보존

**상대 분석 «우리 11»** — 전에는 포메이션을 4-2-3-1 로 고정하고, 선발이 없으면 출전 가능 선수를 명단 순서대로 11명 잘라
자리 순서대로 앉혔다(첫 선수가 GK 자리). 토큰에는 pid 도 편집기도 없어 고칠 길이 없었고, 편집이 막힌 이유(자료 확인 중·선수 계정·권한)도 조용히 삼켰다.
이제 선발 명단만 놓고(없으면 안내하고 아무것도 놓지 않는다), 이 경기의 포메이션을 쓰며, 포지션 → 자리(정확 → 세부·기본 → 라인 → 빈 자리)로 앉힌다.
토큰을 탭하면 번호(상대는 포지션도)·삭제 편집기가 열리고, 막힌 조작은 이유를 토스트로 알린다.

**작전판 세부 포지션** — 포메이션 자리 라벨(LCM·RCM·LWB·RWB·LM·RM·ST)이 선수단 편집기 목록에 없어 «자리 없음»으로 떨어졌고,
자리 없는 포지션은 한 기본 좌표에 한 줄로 늘어섰다(코치 «한쪽에 몰린다»). 선수단·스카우트 포지션 목록에 LDM·RDM·LCM·RCM 을 넣고
(기존 팀에는 자동 보충), 4-2-3-1 더블 피벗을 LDM·RDM 으로 라벨링했다. 자동 배치는 두 번 돈다 — 정확히 같은 자리 → 세부↔기본(CM↔LCM, DM↔LDM).
한글·사용자 정의 포지션 이름(«좌측 풀백»)도 코드로 읽는다. 팀 구성 탭은 세부 포지션을 기본 자리(DM·CM)로 세운다. 선수단 «적용» 버튼이 MouseEvent 를 옵션으로 넘기던 것도 고쳤다.

**애니메이션 장면 덮어쓰기** — 영상·GIF 내보내기는 재생 플래그 없이 두 장면 사이의 중간 좌표를 화면에 올린 채 프레임마다 쉰다.
그 사이 마지막 편집이 남긴 400ms 라이브 저장·탭 전환 플러시·다른 UI 동작이 활성 장면에 중간 좌표를 찍었다(셸에서 재현: 장면 2 의 선수 6명 좌표 변경).
내보내기 동안 `__animExport` 를 켜 자동 저장·라이브 저장·읽기 경로의 «활성 장면 확정»·뷰 스냅을 모두 건너뛰고, 예외로 끝나도 판을 되돌린다.
썸네일 재생성이 토큰 드래그 중에 판을 갈아끼우지 않게도 막았다. 코치가 본 정확한 손 순서는 아직 확인하지 못했다 — 내보내기 없이도 재현되면 다시 본다.

검증: Node 회귀 통과. 셸(app.html) 로컬 프리뷰에서 내보내기 흐름 재현 → 가드 뒤 0건, 평소 드래그 저장 정상. 실기기·실팀 자료는 미확인.

## 2.751 도크 정렬과 경기 기록 화면

- 데스크톱 하단 도크는 기존 버튼·아이콘·순서를 유지하며 세 행을 36px로 맞추고 묶음 간격만 정리합니다. 터치 화면의 줄바꿈과 접기 동작은 유지합니다.
- 700px 이하 경기 화면은 상대 분석·경기 준비·경기 리뷰를 한 줄로 보여줍니다. 단계별 기본 기록 수와 현재 선택은 계속 보입니다.
- 리뷰의 ‘다음 훈련’은 과제 추가와 과제/결과 열기의 역할을 구분하고, 날짜·조·행동·결과를 간결하게 보여줍니다. 훈련 과제에 옮긴 행동·결과는 선수가 읽는 팀 일정에 저장되며 리뷰 원문은 자동 복사하지 않습니다.
- 기록 충족 안내는 ‘리뷰 작성됨’으로, 공개 설정은 별도로 표시합니다. 저장 성공 여부는 기존 저장 상태 표시를 따릅니다.

## 2.785 IDP 선수 상세의 경기 탭

팀 운영 → IDP → 선수 선택에서 이야기 옆의 **경기** 탭으로 이 선수가 남긴 자기 리뷰·평점·역할·출전 기록을 바로 읽습니다. 다른 선수로 이동해도 경기 탭을 유지합니다. 개인 IDP 화면으로 이동하거나 선수 원문을 편집하지 않습니다.

선수 ID와 연결된 계정 하나의 문서만 읽으며, 미연결·중복 연결·문서 미도착·손상·빈 기록을 구분합니다. 경기 일정에서 찾지 못한 기록도 원문을 보존하고, 작성 시각을 경기 날짜로 추정하지 않습니다. 모바일에서도 경기 탭과 기존 이야기·평가·공통질문 탭을 함께 제공합니다.

## 2.788 반복 표시 정리

출석 머리의 중복 집계 숫자와 일정 없는 날의 반복 안내, 오늘의 빈 세션에 덧붙던 빈 훈련 블록 안내를 줄였습니다. 개인 노트의 문서 보관함은 같은 곳을 여는 상단 버튼을 없애고 ‘보관함 훈련’ 탭을 유지합니다. 학습 카드의 미구현 사전 안내를 제거했습니다. 기존 기록·입력·학습 초기화 기능·팀 메뉴·보드 도구는 유지합니다.

## 2.789 이야기 통합과 반복 화면 정리

IDP 선수 이야기를 하나의 기록 목록으로 통합했습니다. 기존 프로필에만 있던 답장과 다음 분기 시작 동작은 이야기로 옮겼고, 긴 답변·과거 기록·상태만 남은 기록도 보존합니다. 기존 강점은 무기 후보로 사용할 수 있으며 원문은 유지합니다. 목표 요약·탐색 안내·인쇄 설명의 반복 표시를 줄였습니다.

훈련 집중 항목, 운동 강도 안내, 분석 화면, 플레이북, 경기 재생과 평가 화면의 중복 설명을 정리했습니다. 분석 화면의 추가 버튼은 기존 입력 창을 바로 엽니다. 보드 도구와 경기 탭은 유지합니다.

검증은 격리된 가상 자료로 진행했습니다. 스카우팅 후보·포인트 통합은 구버전 앱이 원본을 덮어쓰지 못하도록 서버 보호를 검증한 후 별도 배포합니다.

## 2.790 후보·포인트 원본 통합 — 서버 보호 확인 전 배포 대기

스카우팅 기본 정보와 포인트 평가 원본을 기존 운영진 전용 `cs_scout_targets_v1` 안의 후보 기록으로 통합합니다. 보드 배치는 후보 ID를 참조하며, ‘보드에서 내리기’와 ‘후보 보관’을 구분합니다. 서로 다른 기본 정보, 배치 평가·메모, 이전 질문의 점수를 보존하며 프로필에서 확인합니다. 후보 프로필의 ‘스카우팅 포인트’에서 설정한 질문으로 해당 후보를 평가합니다.

기기 전용 `cs_scoutdb_v1`은 팀 소유권을 입증할 수 없어 자동으로 가져오지 않습니다. ‘이 기기의 예전 자료 가져오기’에서 후보·질문 세트를 선택하고 원문을 보존한 채 현재 팀의 운영진 전용 자료로 가져옵니다. 계정·팀·권한과 서버 원문, 기기의 두 저장소 확인이 끝나야 편집을 엽니다. 후보 자료를 팀 선수단이나 공개 IDP로 보내지 않습니다. 새 사진은 후보 원본에서 읽으므로 이전 버전에서는 후보 사진이 보이지 않을 수 있습니다.

새 클라이언트는 서버 판본을 비교해 후보 원본과 변경 이력을 합칩니다. 하지만 이미 열린 구버전 클라이언트가 서버에 직접 저장할 때는 새 클라이언트의 병합을 거치지 않습니다. 따라서 서버의 기존 후보 원본·이력을 없애는 갱신을 차단하는 `migrations/20260913_scout_registry_guard.sql`의 운영 적용과 검증이 릴리스 전제입니다. 이 보호는 UPDATE 대상이며 팀 삭제 등 기존 DELETE 정책을 변경하지 않습니다. 서버 적용·검증 전에는 운영과 같은 서버를 쓰는 미리보기도 배포하지 않습니다.

추가 회귀는 `tests/scouting-store.test.cjs`, `tests/scouting-sync.test.cjs`, `tests/browser/scouting-integration.mjs`에 있습니다. 격리된 가상 자료로 원문·과거 평가·사진 변경 보존, 후보 평가·보관과 복원, 저장 실패·권한·동시 편집 경계를 확인합니다. 운영 서버 보호 적용 여부와 실제 팀 동기화 확인은 별도입니다.

후보 문서는 기존 동기화 한도인 1,500,000자를 따릅니다. 한도를 넘는 새 사진·가져오기는 기기 저장 전에 거부하며 기존 원문을 유지합니다. 두 기기의 이력을 합친 결과나 기존 문서 자체가 한도를 넘으면 원본을 버리지 않고 동기화를 보류합니다. 이 경우 원본을 분리 보관하는 추가 저장 구조가 필요하며, 후보 보관만으로 과거 원문 용량이 줄어드는 것은 아닙니다.

운영 서버의 읽기 전용 점검에서 후보 읽기와 쓰기 정책의 범위 차이를 확인했습니다. 별도 `migrations/20260913_scout_write_scope.sql`은 후보 키의 authenticated INSERT·UPDATE·DELETE에 기존 후보 읽기 조건을 추가하는 제한 정책이며, 다른 키·기존 함수·테이블 권한은 바꾸지 않습니다. 2026-09-13 명시적 승인 후 운영 프로젝트에 보호 트리거와 제한 정책을 설치했습니다. 카탈로그·TEMP text/jsonb 검사와 실제 authenticated 역할의 가상 자료 15개 권한 검사를 통과했고 검증 자료는 롤백했습니다. 검사 함수 두 개의 PUBLIC 실행 권한은 입력받은 JSON 비교에만 사용됩니다. 실제 로그인 토큰·REST 전체 흐름과 실물 기기 현장 검증은 별도입니다.

같은 운영 테이블에서 새 가상 UUID를 사용한 원본 보존 결합 검증 10개도 통과했습니다. admin/executive 정상 수정과 구버전 UPDATE·UPSERT·혼합 요청 거부를 구분하고, 거부 후 원문과 갱신 번호 및 다른 키의 값이 유지됨을 확인한 뒤 전체 롤백했습니다.

## 2.792 관리자 운영 화면

## 2.793 보관함 작전판과 작업 보드 분리

보관함에서 작전판을 열어도 작업 보드의 선수 배치·페이지·애니메이션·되돌리기 기록을 유지합니다. 보관함에서 보는 동안 그 내용을 작업 보드의 자동 저장이나 복구 사본에 기록하지 않으며, 보드로 돌아오거나 보관함 항목을 닫을 때 기존 작업을 복원합니다. 빠르게 다른 항목으로 이동해도 이전 항목의 지연 로딩이 현재 화면을 덮지 않습니다. 보관함 편집과 저장은 해당 자료에 계속 적용됩니다.

검증: Node 1,027개 통과. 외부 연결을 차단한 가상 자료로 WebKit·Chromium의 393/1024/1280px에서 열람·전체화면·빠른 복귀·다른 메뉴 이동·편집 저장·새로고침을 확인했고, 빈 보드도 유지됩니다.

## 2.794 아이패드 팀 IDP 진입

아이패드의 600px 이하 창에서는 하단 팀 메뉴에 IDP를 바로 표시합니다. 일반 아이폰의 기존 여섯 탭과 더보기 진입은 유지합니다. 같은 창에서 권한 자료가 늦게 도착하거나 바뀌어도 인증·동기화 이벤트를 받아 팀 메뉴를 다시 판정하며, 실제 선수 권한에는 코치 메뉴를 열어 주지 않습니다.

팀 IDP를 누른 뒤 선수 문서·평가 항목·명단이 아직 없더라도 팀 화면을 유지합니다. 기존 팀 명단 요청이 로딩·빈 상태·실패/재시도를 표시하며, 개인 IDP로 자동 전환하지 않습니다.


## 2.795 큰 개인 자료 동기화

개인 노트·필기 용지·매치데스크의 원문 전송 한도를 1.5M자에서 12M자로 늘립니다. 기존 JSON과 판본 비교 저장(CAS)을 유지하여 다른 기기에서도 그대로 읽습니다. 새 PDF 가져오기는 노트 전체 11.5M자에서 멈춰 이후 필기 여유를 남깁니다. 기존 PDF 한 번당 렌더링 한도는 유지합니다.

크기 검사는 실제 올릴 자료에만 적용합니다. 같은 자료·변경 없는 자료·서버에서 내려받는 자료를 크기로 막지 않습니다. 한도를 넘는 자료는 원문과 전송 대기를 보존하고, 다른 개인 자료는 서버 확인 후 확정합니다. 오류에는 고정된 자료 종류만 표시하며 문서 제목이나 본문은 노출하지 않습니다.

2026-09-13 운영 카탈로그를 읽어 ps_kv의 크기 제약과 개인 키 크기를 제한하는 트리거가 없음을 확인했습니다. 이번 변경은 서버 스키마·권한·실제 사용자 자료를 수정하지 않습니다. 12M자보다 큰 새 원문은 여전히 대기 상태로 남고 성공으로 표시하지 않습니다.

## 2.796 스카우팅 세션 없을 때 예외 · 일지 ‹ › 읽기 이름

세션이나 팀 권한이 없는 상태로 스카우팅을 열면 후보 저장소 클라이언트의 prepare() 가 read() 를 동기로 부르다 context() 에서 던져 then/catch 에 걸리지 않았습니다(콘솔 uncaught «팀의 후보 자료와 권한을 확인 중입니다» 3건). 동기 예외를 거부(Promise.reject)로 바꿔 호출부의 catch 가 대기 안내를 그대로 띄웁니다. 자료·권한 판정은 바꾸지 않습니다.

선수 일지의 날짜 옆 ‹ › 버튼 읽기 이름이 보기와 상관없이 «이전 달·다음 달»이던 것을 보기 단위(날·주·달·해)로 맞췄습니다(선수 피드백 ⑧).

## 2.797 작전판 장면 띠 ←/→ 이동

장면을 클릭한 뒤 키보드 ←/→ 로 이전·다음 장면을, Home/End 로 첫·끝 장면을 불러옵니다(사용자 요청). 장면 요소에 화살표 처리는 있었지만 장면을 고르면 띠가 다시 그려져 초점이 body 로 돌아가 키가 닿지 않았습니다. 2.028 의 장면 띠 문맥(_afCtx: 띠를 마지막으로 만졌을 때만)에서 창 keydown 으로 받고, 다른 곳을 누르면 원래대로 선택 항목 미세 이동으로 돌아갑니다. 입력칸 안·⌘/Ctrl/Alt 조합·애니메이션 바 닫힘은 제외.

## 2.798 선수 문서가 기기에 없을 때 — 앱이 스스로 받는다

아이패드에서 팀 IDP 선수단이 «계정 연결 안 됨 43명»으로 보인 일(2026-09-13 밤). 서버는 문서 39개를 내주고 권한표도 맞는데 그 기기에 선수 문서(cs_idp_v1_*)가 없던 것이라, 문구가 원인을 엉뚱한 데(권한)로 보냈고 사용자는 로그아웃·재로그인을 해야 했다.

- 선수단 표 아래 문구를 둘로 나눈다: 권한표에 계정이 없는 선수는 «계정 연결 안 됨 n명», 계정은 있는데 이 기기에 문서가 없는 선수는 «선수 문서 아직 안 받음 n명 — 서버에서 받는 중…».
- 문서가 없는 선수가 있으면 IDP 프레임이 셸에 알리고(20초에 한 번), 셸이 동기화 한 회차를 돌린다(45초에 한 번). 받은 뒤에도 없으면 서버 이벤트 `idp_docs_missing`(관리자 › 오류, error_code 에 «n건/전체:마지막 단계»)로 남기고 표에는 «받지 못했어요 · 앱 설정 › 동기화 진단»으로 바꾼다.
- 동기화 진단(syncDiagnostic)이 콘솔에만 남던 것을 최근 40건 기억해 진단 시트에 «최근 진단»으로 보이고 `PSSync.diagLog()`로 읽는다.

문서·권한·서버 판정은 바꾸지 않는다. 받기는 기존 pull 경로(loc==null → 받음)를 그대로 쓴다.

## 2.803 팀 운영 › IDP(폰) — 선수당 한 장

사용자: «팀 운영에서 IDP 들어갔을 때도 선수들이 쓴 거 더 잘 보고 싶어 · 모바일». 실측(375px): «오늘 한 장» 표가 920px 라 321px 안에서 가로로 세 배 스크롤, 한 마디는 잘리고 누를 것 46개 중 43개가 40px 미만.

폰 폭(<640)에서는 표 대신 목록: 선수마다 한 장 — 번호·이름·그 날 칩·❤·› 한 줄, 아래 이번 주 초점 한 줄, 그 아래 **한 마디 전문**(15px, 줄바꿈 그대로). 정렬(한 마디·몸 나쁨·아직 사흘+ 먼저)·자료·❤/› 핸들러는 표와 같다. 출석 칩과 답 입력칸은 폰에서 걷는다(출석 화면·선수 이야기에서). 폰은 «이번 주» 표 대신 늘 이 목록. 데스크톱·아이패드 표는 그대로.

## 2.804 토큰 시트 — 포지션 고르기

사용자: «모바일 보드는 토큰의 이름과 번호 수정, 포지션 수정 가능하게». 실측: 폰 시트의 번호·이름 칸은 이미 동작(탭 → 키보드 → 반영). 포지션은 어디에도 편집 칸이 없었다(`p.pos` 는 포메이션 배치와 선수단 연동으로만 채워짐).

- `.sel-ctl` 에 `#posSel`(SQ_POS 21개 + «포지션» 비움 + 숨은 «여러 값») — 폰 시트 1줄(번호 72 · 포지션 92 · 이름 · ⋯)과 데스크톱 열 둘 다. 고르면 선택 선수(여럿이면 전부)의 `pos` 를 바꾸고 되돌리기에 남긴다.
- 포지션을 고를 때 토큰이 번호 표시 모드면 포지션 표시(`state.label="pos"`, `convertPosVocab` 경유)로 바꾸고 토스트. 폰엔 보드 설정이 없으므로 ⋯ 줄에 «번호 표시 / 포지션 표시» 토글을 둔다. 데스크톱은 설정 › 선수 › 표시 그대로.
- 번호·이름 편집은 그대로(2.711).

## 2.805 색상 팔레트 — 직접 고른 색을 고정색으로

사용자(코치): «고정색에 원하는 색(회색 등)을 추가해 두고 쓰게. 매번 전체 색상에서 다시 고르고 있다». 팔레트는 유니폼 4색 + 고정 6색 + 직접 고르기(색상환) + 되돌리기였다.

- 색상환에서 색을 고르면(change) 그 색이 고정색 뒤에 «내 색»으로 남는다(`cs_my_cols_v1`, 최근 6개, 같은 색은 한 번, 점선 테두리). 누르면 그 색 적용(선택 하나·여럿 모두), 길게 누르거나(0.6초) 오른쪽 클릭하면 뺀다.
- 기기 저장(환경설정처럼). 팀 자료·서버·다른 기기 영향 없음.

## 2.806 모바일 로그인 — 계정 선택과 이전 응답 보호

모바일에서 Google을 눌러도 카카오 계정으로 돌아오는 것 같다는 제보를 확인했다. 실제 인증 시작 응답은 Google → Google, Kakao → Kakao로 분리되어 있으며, 제보 기기의 화면 전환 자체는 재현하지 못했다. 별도로 이전 로그인의 사용자 조회가 늦게 도착하면 새 세션의 UID·이메일을 덮을 수 있는 경합을 재현해 수정했다.

- OAuth 콜백과 초기 사용자 조회는 요청 당시 토큰·로그인 세대·UID가 현재 세션과 일치할 때만 적용한다. 정상 토큰 갱신과 오프라인 캐시 부팅은 유지한다.
- Google 로그인과 로그인 방법 추가에 계정 선택 화면을 요청한다. 두 진입점 모두 Google/Kakao만 허용하고 iframe에서 시작해도 앱 최상위로 돌아온다.
- 로그인된 메뉴의 ‘Google 연결’을 ‘Google 로그인 추가’로 명확히 하고, 같은 팀·자료에 접근하는 방법을 추가한다는 설명을 붙였다.
- 지연 응답·로그아웃·토큰 갱신·콜백 역전은 실제 함수 회귀로, 모바일 버튼은 격리된 실제 앱에서 WebKit/Chromium 터치로 검증한다. 실제 사용자 로그인·계정 연결·자료는 변경하지 않는다. 기존에 잘못 저장된 세션은 이번 가드가 자동 교정하지 않으므로 업데이트 후 재로그인이 필요하다.

## 2.807 훈련 편집기 — 하단 보관함 저장 겹침

훈련 세션 만들기의 하단 왼쪽에 공용 작전판 ‘보관함 저장’ 버튼이 나타나 설정·되돌리기 도구를 덮었다. 도구 정렬용 공통 CSS가 편집 중 숨김 규칙보다 우선해 버튼을 강제로 표시한 것이 원인이다.

- 정렬 규칙에서 공용 저장 버튼만 제외해 기존 화면별 표시 조건을 복원했다. 훈련은 상단 ‘저장하기’를 사용하고, 일반 작전판은 기존 ‘보관함 저장’을 사용한다.
- 저장 처리·자료 구조·도크 크기·도구 순서는 변경하지 않는다.
