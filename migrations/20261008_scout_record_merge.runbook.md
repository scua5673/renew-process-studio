# 20261008 — 선수단 기록 서버 합치기 (유료 전환 문턱 4번 «항목 단위로»의 1단계)

## 왜 «키 쪼개기» 대신 «서버 합치기»인가

가용인원 기록(`meta.statusRuns`·`participationDays`·`injuryInfo`)은 선수단 문서(`scout_tool_v1`) 한 통에 들어 있다.
낡은 사본을 든 기기가 저장하면 그 사이 쌓인 날이 통째로 사라졌다(2.948 — 9/6~10/6 15팀 34건, 10/7 손으로 복구).

| 길 | 장점 | 막히는 곳 |
|---|---|---|
| A. 서버 합치기(이 파일) | 문서 모양 그대로 · **모든 판에 바로 듣는다** · 앱 코드 변경 0 | 기록을 일부러 지우는 기능은 만들 수 없다(지금도 없다). 같은 날을 두 코치가 다르게 고치면 나중 저장이 이긴다(지금과 같다) |
| B. 기록을 항목 키로(`sr:<선수>`) | 진짜 항목 단위 · 동시 편집에 강함 | 옛 판이 meta 칸을 다시 만들어 덮는다 → 판 하한을 새 판까지(10/7 실측: 72시간 사용자 42% 차단) · 선수에게 부상 기록을 숨기는 읽기 규칙을 여러 SQL 정의에 새로 걸어야 한다(`ps_can_read_key` 기본값이 «읽기 허용») · 수 주 작업 |

**A 를 먼저, B 는 옛 판이 빠진 뒤**(관리자 «7일 판 분포»에서 2.948 이상이 95% 넘을 때) 다시 본다.
A 를 깔아 두면 B 로 옮기는 동안에도 기록이 지켜진다.

## 규칙

- `scout_tool_v1` UPDATE 에서, 새 판 meta 에 그 칸이 **있을 때만**(칸이 통째로 없으면 20261006 가드가 이미 거부한다).
- statusRuns: 서버 판에 있는 (선수·날)이 새 판에 없으면 되살린다. 새 판에 있는 날은 새 판이 이긴다(과거 날 정정 그대로).
  되살린 선수만 날 단위로 다시 구간으로 묶는다 — 손대지 않은 선수의 배열은 바이트 그대로.
- participationDays·injuryInfo: 칸이 새 판에 없거나 서버 칸의 `at` 이 더 늦으면 서버 것. 같으면 새 판.
- 잃은 것이 없으면 새 판을 **바이트 그대로** 둔다. 합치다 오류가 나면(깨진 날짜 등) 새 판을 그대로 받는다 — 저장을 막지 않는다.
- cupd 는 새 판 것 그대로: 올린 기기는 «확인됨», 다른 기기는 실시간 핑으로 합친 판을 받는다.
  ⚠ 올린 기기 자신은 다음에 서버가 바뀔 때까지 자기 (모자란) 사본을 본다 — 그 기기가 다시 저장해도 서버가 또 합친다.
- 되살린 날이 있으면 데이터 사고 기록장(20261007)에 `near_miss` 를 팀·하루 한 줄.

## 적용 (SQL 편집기, 사람이)

1. **먼저 20261007_incident_ledger 를 적용**(기록장이 없어도 합치기는 되지만 기록이 안 남는다).
2. `20261008_scout_record_merge.sql` 전체 실행.
3. `20261008_scout_record_merge.verify.sql` — 기대: `merge_trigger O` · 순서 `ps_00c_noop_guard_t < ps_00c_scout_record_guard_t < ps_00d_scout_record_merge_t` (그 앞 계보·판·모양 가드도 함께 보인다) · `secdef true` · `pure_fns 6` · `runs_lost 2 · days_lost 1 · inj_lost 1 · keep_null true`.
4. 다음 날: 관리자 백엔드 «데이터 사고»에 near_miss 가 생겼는지 · 관리자 오류 탭에 `sync_server_rejected` 가 scout_tool_v1 로 늘지 않았는지.

되돌리기: `20261008_scout_record_merge.rollback.sql`(트리거·함수만, 데이터 그대로).
