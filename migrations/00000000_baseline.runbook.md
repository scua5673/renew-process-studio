# 00000000_baseline — 운영 데이터베이스 구조 기준본

이 저장소만으로 운영 데이터베이스의 «우리가 만든 구조»를 다시 세울 수 있게 하는 파일 묶음이다.
2026-09-13 이전 변경은 `migrations/` 가 아니라 문서 저장소(`supabase-설치/`·루트 `supabase-*.sql`)에 흩어져 있고,
그 파일들이 운영과 다르다는 것도 실제로 확인됐다(2.912: 운영 `ps_can_write_key` ≠ 저장소 파일).
그래서 «파일을 순서대로 다시 실행»하는 대신 **운영 카탈로그에서 지금 구조를 그대로 뽑아** 기준본으로 둔다.

| 파일 | 무엇 |
|---|---|
| `00000000_baseline.catalog.sql` | 읽기 전용 추출 쿼리. 카탈로그만 읽고 행 값은 읽지 않는다. DDL 텍스트 한 칸(`ddl`)을 돌려준다 |
| `00000000_baseline.sql` | 그 결과(운영에서 받은 것). **손으로 고치지 말 것** |
| `00000000_baseline.local-test.cjs` | 합성 PGlite 왕복 시험 — 추출 → 빈 DB 에 적용 → 다시 추출이 바이트 단위로 같고, 행 단위 보안 판정도 같은지 |
| `../scripts/schema-baseline.mjs` | 운영에 추출 쿼리를 묻고 기준본을 저장한다. `--check` 는 운영과 저장본을 비교만 한다 |

## 받기 · 비교

준비(한 번): Supabase 개인 접근 토큰을 만들어 `~/.supabase-pat` 에 둔다(`supabase-설치/SQL실행.command` 와 같은 파일).
<https://supabase.com/dashboard/account/tokens> → 아래 한 줄. 토큰은 화면·저장소 어디에도 남기지 않는다.

```bash
printf '%s' 'sbp_…' > ~/.supabase-pat && chmod 600 ~/.supabase-pat
```

- 새로 받기: `node scripts/schema-baseline.mjs` → `migrations/00000000_baseline.sql` 를 다시 쓴다. 바뀐 줄은 `git diff` 로 본다.
- 운영과 비교만: `node scripts/schema-baseline.mjs --check` → 다르면 첫 차이 줄을 보여 주고 1로 끝난다.
  운영에 SQL 을 손으로 적용한 뒤(새 마이그레이션 실행 뒤) 기준본을 새로 받아 같은 PR 에 넣는다.

## 담는 것 · 안 담는 것

담는 것: 우리 스키마(public 과 Supabase·시스템이 아닌 스키마)의 확장, enum, 시퀀스, 표(기본값·식별 열·생성 열·NOT NULL),
제약(기본키·유일·검사 → 외래키), 함수, 뷰(security_invoker 등 옵션 포함), 색인, 트리거(우리 함수를 부르는 `auth.users` 트리거 포함),
행 단위 보안 켜기/강제, 정책, 표·함수 권한(public·anon·authenticated·service_role), realtime 발행 표, 주석, pg_cron 작업(스크립트가 따로 묻는다).

안 담는 것 — 복원할 때 따로 챙긴다:
- **데이터**(팀·선수 자료). 데이터는 Supabase 백업(Pro: 일 단위)에서 온다.
- Supabase 가 새 프로젝트에 주는 것: `auth`·`storage`·`realtime` 스키마, 역할(anon·authenticated·service_role), `supabase_realtime` 발행 자체.
- 인증 설정(카카오·Google 공급자, 리디렉션 주소, 이메일 템플릿), API 키, Netlify 설정 — 대시보드에서 손으로.
- 도메인·복합 타입·집계 함수·열 단위 권한·타입 주석 — 기준본 맨 끝 «안 담긴 것» 줄이 개수로 알려 준다. 0이 아니면 손으로 옮긴다.
- 스키마 권한·소유자. 복원은 `postgres` 로 실행한다.

## 새 프로젝트에 되살리기(복구 훈련 절차)

1. 새 Supabase 프로젝트(같은 리전·같은 Postgres 메이저 판)를 만든다.
2. SQL 편집기에서 `00000000_baseline.sql` 전체를 실행한다(맨 위 `set check_function_bodies = off;` 덕에 함수·표 순서와 무관).
3. `node scripts/schema-baseline.mjs --check` 의 대상 프로젝트를 새 프로젝트로 바꿔 돌려 차이 0 을 확인한다(`PROJECT_REF`).
4. 데이터: Supabase 백업에서 복원하거나 `pg_dump --data-only` 결과를 넣는다.
5. 인증 공급자·리디렉션 주소·키를 대시보드에서 다시 설정하고, 앱의 `PS_SYNC`(app.html) 주소·publishable 키를 새 프로젝트로 바꾼 미리보기 배포에서 로그인·동기화를 확인한다.

분기마다 한 번 이 절차를 빈 프로젝트에서 실제로 해 보고, 걸린 시간과 막힌 곳을 이 문서 아래에 적는다.
