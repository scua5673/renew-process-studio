# 00000000_baseline — 운영 데이터베이스 구조 기준본

이 저장소만으로 운영 데이터베이스의 «우리가 만든 구조»를 다시 세울 수 있게 하는 파일 묶음이다.
2026-09-13 이전 변경은 `migrations/` 가 아니라 문서 저장소(`supabase-설치/`·루트 `supabase-*.sql`)에 흩어져 있고,
그 파일들이 운영과 다르다는 것도 실제로 확인됐다(2.912: 운영 `ps_can_write_key` ≠ 저장소 파일).
그래서 «파일을 순서대로 다시 실행»하는 대신 **운영 카탈로그에서 지금 구조를 그대로 뽑아** 기준본으로 둔다.

| 파일 | 무엇 |
|---|---|
| `00000000_baseline.catalog.sql` | 읽기 전용 추출 쿼리. 카탈로그만 읽고 행 값은 읽지 않는다. DDL 텍스트 한 칸(`ddl`)을 돌려준다 |
| `00000000_baseline.sql` | 그 결과(운영에서 받은 것). **손으로 고치지 말 것** |

| `20261025_private_reader_restore.local-test.cjs` | 실제 사진 권한·보관함 복구 마이그레이션을 적용한 합성 DB 왕복. 논슈퍼유저 관리자, 전용 함수 소유자, 원문/사진/history RLS, 위험 역할 복원 거부 확인 |

## 받기 · 비교

준비(한 번): Supabase 개인 접근 토큰을 만들어 `~/.supabase-pat` 에 둔다(`supabase-설치/SQL실행.command` 와 같은 파일).
<https://supabase.com/dashboard/account/tokens> → 아래 한 줄. 토큰은 화면·저장소 어디에도 남기지 않는다.

```bash
printf '%s' 'sbp_…' > ~/.supabase-pat && chmod 600 ~/.supabase-pat
```

- 새로 받기: `node scripts/schema-baseline.mjs` → `migrations/00000000_baseline.sql` 를 다시 쓴다. 바뀐 줄은 `git diff` 로 본다.
- 운영과 비교만: `node scripts/schema-baseline.mjs --check` → 다르면 첫 차이 줄을 보여 주고 1로 끝난다.
  운영에 SQL 을 손으로 적용한 뒤(새 마이그레이션 실행 뒤) 기준본을 새로 받아 같은 PR 에 넣는다.

## 담는 것 · 안 담는 것

담는 것: 우리 스키마(public 과 Supabase·시스템이 아닌 스키마)의 확장, enum, 시퀀스, 표(기본값·식별 열·생성 열·NOT NULL),
제약(기본키·유일·검사 → 외래키), 함수, 뷰(security_invoker 등 옵션 포함), 색인, 트리거(우리 함수를 부르는 `auth.users` 트리거 포함),
행 단위 보안 켜기/강제, 정책, 표·함수 권한(public·anon·authenticated·service_role), realtime 발행 표, 주석, pg_cron 작업(스크립트가 따로 묻는다).
예외적으로 앱이 관리하는 **`ps_blob_reader_v1` 한 역할**과 그 역할 소유 함수의 소유자도 담는다. 사진 권한 함수가 복원자의 `postgres` 소유가 되면 `SECURITY DEFINER` 안에서 원문 RLS를 우회할 수 있어, 일반 소유자와 달리 생략하지 않는다.

안 담는 것 — 복원할 때 따로 챙긴다:
- **데이터**(팀·선수 자료). 실제 백업·PITR의 설정과 복원 가능 시점을 확인한 뒤 별도 복원한다. 이 구조 반출은 데이터 백업이 아니다.
- Supabase 가 새 프로젝트에 주는 것: `auth`·`storage`·`realtime` 스키마, 역할(anon·authenticated·service_role), `supabase_realtime` 발행 자체.
- 인증 설정(카카오·Google 공급자, 리디렉션 주소, 이메일 템플릿), API 키, Netlify 설정 — 대시보드에서 손으로.
- 도메인·복합 타입·집계 함수·열 단위 권한·타입 주석 — 기준본 맨 끝 «안 담긴 것» 줄이 개수로 알려 준다. 0이 아니면 손으로 옮긴다.
- 일반 스키마 권한·소유자, 다른 사용자 정의 역할과 비밀번호. 아래 전용 reader 예외만 자동 복원한다.

## 사진 RLS reader 복원 전제

`ps_blob_reader_v1`은 `NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS INHERIT`로 만든다. `authenticated`만 상속하고 `public`·`auth`의 USAGE만 받는다. 일반 로그인 역할에게 reader membership을 주지 않는다. 기존 관리자의 역할 관리 membership은 비슈퍼유저 `CREATEROLE/BYPASSRLS` 관리자 범위에서만 허용한다.

복원자는 역할 생성, `authenticated` membership 부여, `public`·`auth` USAGE 부여, 자신이 복원한 함수의 소유자 변경을 할 수 있어야 한다. Supabase의 `postgres`처럼 **슈퍼유저가 아니어도** 가능한 최소 전제이며, 이러한 권한이 없는 계정으로 우회해 실행하지 않는다. 역할·스키마·소유자 상태가 예상과 다르면 먼저 원인을 확인한다.

PostgreSQL은 함수 소유자 변경 때 새 소유자의 스키마 CREATE와 복원자의 SET ROLE 권한을 요구한다. PG16+에서 CREATEROLE로 만든 역할의 자동 관리 membership은 SET을 허용하지 않을 수 있다. 생성 DDL은 함수 정의 직후의 **단일 원자적 DO**에서 필요한 동안만 SET/CREATE를 부여하고 소유자를 바꾼다. 같은 DO 안에서 reader 역할로 함수 ACL과 주석을 적용한 뒤 복원자로 돌아와 임시 권한을 회수한다. 자기 grantor membership이 원래 있었으면 ADMIN/INHERIT/SET 세 옵션을 모두 보존하고, 새 임시 행이면 완전히 제거해 INHERIT나 빈 membership 행도 남기지 않는다. 기존 SET 권한은 유지하며 최종 reader에는 CREATE가 남지 않는다. DO가 실패하면 임시 권한도 함께 롤백된다.

원본 또는 대상 reader가 로그인·슈퍼유저·RLS 우회·DB/역할 생성·복제 권한, 다른 상위 역할, 스키마/DB CREATE, 원문/파생 표·스키마 소유권을 가지면 복원을 거부한다. 원본의 `ps_blob_can_read_v1` 소유자가 reader와 달라도 거부한다. 카탈로그 SELECT는 안전하지 않은 원본에 대해 실행 시 거부하는 DDL을 반환하므로, 이를 지우거나 소유자를 `postgres`로 바꿔 통과시키지 않는다. 기준본 반출은 계속 카탈로그 읽기 전용이며 운영 역할을 만들거나 수정하지 않는다.

## 새 프로젝트에 되살리기(복구 훈련 절차)

1. 새 Supabase 프로젝트(같은 리전·같은 Postgres 메이저 판)를 만든다.
2. 위 관리자 전제를 확인한 **빈 프로젝트**의 SQL 편집기에서 `00000000_baseline.sql` 전체를 실행한다(맨 위 `set check_function_bodies = off;` 덕에 함수·표 순서와 무관). 전용 reader의 역할·소유자 복원 블록을 생략하지 않는다.
3. `node scripts/schema-baseline.mjs --check` 의 대상 프로젝트를 새 프로젝트로 바꿔 돌려 차이 0 을 확인한다(`PROJECT_REF`).
4. 데이터: Supabase 백업에서 복원하거나 `pg_dump --data-only` 결과를 넣는다.
5. 인증 공급자·리디렉션 주소·키를 대시보드에서 다시 설정하고, `docs/ENVIRONMENTS.md`의 명시적 test backend로 만든 미리보기 배포에서 합성 사용자·팀으로 로그인·동기화를 확인한다. 운영 주소·키를 소스에서 임시 교체하거나 실제 계정의 기기 저장소를 지우지 않는다.
6. `ps_blob_can_read_v1`의 소유자가 `ps_blob_reader_v1`인지, reader가 RLS를 우회하지 않고 CREATE를 갖지 않는지 확인한다. 비공개 원문과 사진은 타인에게 모두 거부되고 소유자에게 모두 보이는지 함께 확인한다. 아래 합성 시험은 이러한 복원 계약을 검증하며, 실제 백업의 복원 훈련·RPO/RTO 증거를 대신하지 않는다.

분기마다 한 번 이 절차를 빈 프로젝트에서 실제로 해 보고, 걸린 시간과 막힌 곳을 이 문서 아래에 적는다.
