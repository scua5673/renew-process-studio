# 보관함 원문 복구

이 변경은 보관함의 현재 자료를 덮어 되돌리지 않는다. 보관함의 **복구**에서 내 기록을 선택하면 같은 공간에 새 비공개 자료를 만든다. 공유 폴더, 원래 항목 ID, 경기 연결은 물려받지 않는다. 본문과 사진 참조, 장면/페이지는 보존한다. 현재 자료나 복구본을 이후 수정·삭제한 경우 같은 요청을 재시도해도 다시 만들거나 덮지 않는다.

## 저장과 권한

- `ps_library`의 의미 있는 UPDATE와 모든 DELETE 전에 OLD 행 전체를 `ps_library_history`에 보관한다. `updated_at`, `saved_at`, `item.savedAt`만 바뀐 자동 저장은 새 이력으로 세지 않는다. 본문·이름·페이지·사진·폴더·태그·공유·소유권 변경은 계속 보관하고, 보관되는 snapshot은 시각을 포함한 OLD 행 전체다. 기존 KV 이력의 시간 간격 샘플링을 재사용하지 않는다.
- 양쪽 기기 변경을 발견한 앱은 서버 본문을 받기 전에 기기의 전체 사본을 owner-only archive RPC에 보관한다. 확인 실패, 계정/공간 전환, 새 기기 편집이 감지되면 원문 교체를 멈춘다. 서버의 UPDATE 전 원문은 트리거가 별도로 보관한다.
- 이력은 당시 `owner_id`인 현재 회원만 읽는다. 현재 또는 과거 항목이 공유였더라도 이력을 팀에 공유하지 않는다. 소유자가 없던 구자료를 현재 호출자의 소유라고 추정하지 않는다. 퇴단하면 본문·사진·복구 권한이 사라진다.
- 복구와 충돌 archive는 모든 사진 참조를 `ps_blob_assert_refs_v1(..., NULL)`로 검사한다. 복구는 실제 사진 행의 존재도 확인한다. 원문 사진이 누락되면 새 자료를 만들지 않고 성공으로 표시하지 않는다. 기존 KV 되돌리기도 남은 `thumbRef`/`emblemRef`가 있으면 현재 문서를 유지한다.
- 기기 사진 캐시는 `ps_blob:<uid>:<workspace>:<hash>`로 읽고 쓴다. 이전의 전역 `ps_blob:<hash>`는 소유권 증거가 없어 읽거나 자동 삭제하지 않는다. 정상 서버 권한으로 다시 받은 사진만 새 범위에 보관한다. 응답과 IDB 쓰기는 출발 계정·공간·소유권 seal·전환 epoch를 재검사한다.

## 적용 순서와 한계

SQL은 `20261025_library_recovery.sql` 다음 `20261025_private_blob_boundary.sql` 순서로 적용한다. 두 migration의 사전 점검과 검증 SQL을 사용한다. 복구 RPC는 사진 권한 migration 없이 실행되지 않게 닫혀 있다. 앱은 `library-recovery.js`를 `sync.js` 앞에 읽는다.

설치 뒤의 변경부터 이력이 쌓인다. 설치 전에 이미 제거된 본문이나 사진을 이 기능으로 재생성할 수는 없다. 팀·계정 삭제 복구나 관리자 복구 권한은 이번 변경에 포함하지 않았다. 롤백은 복구 RPC의 앱 실행 권한을 거두며 이미 보관한 이력과 현재 자료를 삭제하지 않는다.

## 용량 관측과 보존 기간

이력의 보존 기간은 아직 정하지 않았으며 자동 삭제·개수 제한·시간 간격 샘플링을 하지 않는다. 운영에서는 일별 이력 개수와 표·인덱스·TOAST 용량, snapshot 크기의 p95·최댓값, 항목별 하루 이력 증가량, 이력 INSERT·저장 공간 오류를 원문 내용 없이 집계해 관측한다. 사용자의 보존 정책을 정하기 전에 과거 원문을 자동으로 버리지 않는다.

사진이 모두 작은 참조인 것은 아니다. 현재 1,900,000자를 넘는 사진과 별도 분리 대상이 아닌 영상은 본문에 남을 수 있어, 전체 이력의 크기를 함께 관측해야 한다. 이력 쓰기 실패는 현재 행의 변경과 같은 트랜잭션을 실패시키므로 이전 서버 원문은 유지되지만 새 저장이 지연될 수 있다.

## 합성 검증

- `node migrations/20261025_library_recovery.local-test.cjs`: 실제 두 migration을 메모리 PostgreSQL에 적용해 전체 OLD 행, 빠른 연속 편집, 동시 편집 원문, owner/member RLS, 개인/팀 공간, 과거 사진, 누락 사진, 삭제, 재요청 대상의 삭제/공개/소유자 변경을 검증한다.
- `node --test tests/library-recovery.test.cjs tests/history-blob-restore.test.cjs`: 실제 `_syncLibrary`의 archive 선행·실패 보존, 사진 업로드→새 기기 hydrate→다음 회차 dirty 0, 사진만 편집, 지연 캐시 읽기/쓰기, 누락 사진의 성공 거부를 검증한다.
- `tests/browser/library-recovery.mjs`: 외부 요청을 차단한 로컬 fixture에서 양 브라우저 엔진, 375/393/768/1280 화면 폭, 명암, 키보드 복귀, 새 비공개 복구와 현재 원문 보존을 검증한다. 실제 앱의 `historyApply`와 IDB를 지연시켜 계정/팀 전환 뒤 늦은 사진 저장과 legacy cache 재사용을 차단하는지도 확인한다. iPad 768px는 기존 앱 정책에 따라 CSS viewport 1100px를 사용한다.

실제 기기, 운영 데이터베이스, 실계정에는 접근하지 않은 개발 검증이다.
