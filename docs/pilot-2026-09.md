# PROCESS STUDIO 4주 현장 파일럿

작성: 2026-09-12. 아래 숫자는 **시작 전에 합의할 의사결정 기준의 제안**이다. 모집, 실사용 관찰, 유지율·효과·지불 의사 검증은 아직 진행하지 않았다. 배포 및 자동 테스트 통과를 제품 효과의 증거로 삼지 않는다.

## 목적과 표본

새 기능 수 대신, 처음 온 사용자가 도움 없이 결과 하나를 만들고 다음 주에도 그 결과를 이어 쓰는지 확인한다. 중심 질문은 **경기 관찰 → 다음 훈련 실행 → 후속 확인이 한 팀의 실제 업무에서 이어지는가**다.

- 서로 다른 팀 3~5곳. 팀별 담당 코치 1명 이상을 정한다. 보조 코치가 있는 팀과 혼자 운영하는 팀을 함께 포함한다.
- 선수는 전체 표본에서 5~8명. 가능하면 3개 이상 팀에 나눠 모집한다. 팀마다 5~8명이라는 뜻은 아니다.
- 첫날 참석자와 초대 수락자를 고정 명단으로 남긴다. 이미 능숙한 운영자만으로 채우지 않는다. 기존 사용자와 첫 사용자를 구분한다.
- 선수 표본이 작으므로 비율과 함께 항상 `성공 인원/해당 인원`을 적는다. 전체 사용자에게 일반화하거나 통계적 유의성을 주장하지 않는다.
- 개인정보·훈련 내용·평가 원문을 조사표에 옮기지 않는다. 참여 코드(T01/C01/P01), 역할, 기기, 앱 판, 발생 시각, 성공 여부, 도움 요청 수만 남긴다. 담당자가 필요한 동의 및 팀 참여 절차를 진행한다.

## 역할별 첫 성공 과제

과제를 읽어 준 뒤 조작 방법은 설명하지 않는다. 사용자가 요청한 도움은 제공하되 도움 횟수와 막힌 지점을 기록한다. 로그인·초대·팀 접근 시간을 별도로 기록하고, 아래 작업 시간은 해당 화면이 열린 순간부터 잰다. 실제 팀에 가짜 예제 경기나 선수를 심지 않는다. 체험 자료가 필요하면 분리된 테스트 공간에서만 사용한다.

| 역할 | 관찰자가 읽어 줄 과제 | 성공 증거 | 제안 시간 목표 |
| --- | --- | --- | --- |
| 보드를 쓰러 온 코치 | “장면 하나를 골라 선수 위치 한 곳을 바꾸고, 다시 쓸 수 있게 보관하거나 이미지로 내보내세요.” | 새 결과를 다시 열어 변경한 위치를 확인하거나 내보낸 파일을 확인 | 도움 없이 5분 이내 |
| 팀을 운영하는 코치 | “우리 팀의 다음 훈련일을 골라 실제로 할 훈련 하나를 등록하고, 오늘 또는 일정에서 다시 찾아보세요.” | 지정 날짜에 훈련이 보이고 재열람해 내용이 유지됨 | 도움 없이 7분 이내 |
| 초대받은 선수 | “내 팀과 역할을 확인하고, 되고 싶은 모습과 이번에 키울 행동 하나를 정한 뒤 오늘 해봤는지 남겨 보세요.” | 개인 방향과 오늘 기록을 다시 열어 방금 입력을 확인 | 첫 설정 포함 도움 없이 3분 이내 |
| 같은 선수의 두 번째 기록 | “오늘 행동을 시도했는지 기록하세요. 장면 메모는 필요할 때만 남기세요.” | 오늘 선택이 저장되고 화면을 다시 열어도 유지됨 | 핵심 선택 30초·5회 탭 이내 |

시간 측정에 텍스트 입력 시간을 포함한다. 일간 탭 수는 핵심 기록을 위한 이동·선택으로 센다. 선택적인 긴 메모, 몸 상태 확인, 접근성 보조가 필요한 작업은 별도 기록하고 누락해서 빠른 것처럼 보고하지 않는다. 처음 성공하지 못한 사람도 분모에 남긴다.

## 4주 실행 순서

| 주차 | 실행 | 남길 증거 | 다음 주로 가는 조건 |
| --- | --- | --- | --- |
| 1주차 | 위 첫 성공 과제를 각자 수행. 경기일·훈련일을 미리 확인하고 실제 리뷰에서 다음 행동 하나를 훈련일에 연결 | 역할별 소요 시간·도움·막힌 화면, 예정된 팀 활동 기회 | 저장·권한 문제를 먼저 해결. 막힌 과제의 입력/이동 단계를 축소 |
| 2주차 | 코치가 연결 과제를 실제 훈련에서 실행하고 결과 한 줄을 남김. 선수는 예정된 기록일에 기록하고 코치 답변을 확인 | 과제 계획·실행·결과 확인 시각, 선수 기록과 답변 도달 여부, 앱 밖 재입력 | 수행을 못 한 이유를 제품 문제/훈련 취소/일정 불일치로 분리 |
| 3주차 | 다음 경기 리뷰에서 지난 훈련 결과를 다시 확인. 관찰자 없이 같은 흐름을 반복 | 서로 다른 두 번째 사용 주, 코치가 실제로 참고한 결과, 여전히 쓰는 메신저·종이·다른 도구 | 재사용되지 않는 단계는 기능 추가 전에 이유를 관찰 |
| 4주차 | 반복 흐름을 한 번 더 확인하고 15분 인터뷰. 계속 사용할 업무와 중단할 이유를 각각 묻기 | 4주 반복 사용, 팀별 닫힌 연결 수, 반복 우회 작업, 지속 사용 이유 | 아래 기준으로 확대/수정 후 재검증/중단을 결정 |

각 주의 시작·끝을 팀의 현지 시간으로 고정한다. 주 1회 담당 코치와 10분 점검하며, 조사자가 사용을 대신하지 않는다. 일정 취소나 선수 부상·휴식은 실패로 몰지 않는다. 사전에 기록한 활동 기회와 불가 사유를 함께 남겨 결과가 좋게 보이도록 사후 분모를 바꾸지 않는다.

주간 코칭 연결은 달력 때문에 7일 안에 끝나지 않을 수 있다. 같은 주에 완료된 연결은 그 주의 분자에 한 번만 세고, 앞 주에서 이월된 과제임을 표시한다. 처음 관찰부터 후속 확인까지 걸린 날짜도 함께 남긴다. 담당자가 완료 표식만 누른 것은 실행 증거로 부족하며, 훈련 실행과 결과 재열람을 확인해야 한다.

저장 실패율은 모든 저장 시도를 알 수 있을 때만 `실패한 시도/전체 시도`로 산출한다. 현재 억제된 이벤트 행 수를 분모로 삼지 않는다. 이 파일럿에서는 관찰 회차별 저장 시도와 재열람 결과를 조사표에 남기고, 앱 로그는 발생 시각·기기·판본을 대조하는 보조 자료로 사용한다.

## 이벤트 계측 범위와 한계

기존 `PSSync.event(name, {feature, status, meta})`와 `PSSync.act(name, feature)`를 활용한다. 실제 노출 API 이름은 `studio/sync.js`의 `window.PSSync`에서 확인한다. 새로운 실사용 계측은 상태 변경 또는 저장 완료가 확인된 지점에만 둔다. 클릭을 완료로 간주하지 않는다.

- `ps_events` 전송 형식은 유지한다. 본문·메모·평가·위치·선수 이름을 추가 수집하지 않는다. 숫자/불리언과 허용된 짧은 분류 코드만 보낸다.
- 2.748 이벤트 큐는 기기에만 고유 ID·소유 uid를 붙인다. 성공 응답에서 실제 전송 ID만 제거한다. 요청 중 추가된 이벤트를 함께 지우지 않는다. 다른 계정의 대기 이벤트는 해당 계정이 다시 로그인했을 때만 전송한다.
- 소유 uid가 없는 옛 `ps_event_queue_v1`은 다음 로그인에 귀속할 근거가 없어 자동 이관하지 않는다. 큐 변경 시점의 오래된 미전송 제품 이벤트는 지표에서 누락될 수 있다. 경기·IDP 같은 사용자 콘텐츠를 변경하는 처리가 아니다.
- 하루 기능 핑·행동 반복 억제·저장/오류 이벤트 억제는 계정별로 구분한다. 토큰/사용자 조회가 늦게 끝나도 다른 로그인 uid와 섞어 보내지 않는다.
- 큐는 기존처럼 최근 50개 한도다. 행동 이벤트는 20초, 경기/리뷰는 5분 간격 억제와 일일 300건 상한이 있다. `_saved` 성공 이벤트는 10분, 동일 오류는 5분 억제한다. 완전한 사용 이력이나 정확한 시도 횟수가 아니다.
- 브라우저 저장 실패·장기 오프라인·동시 탭 쓰기·응답을 받지 못한 뒤 재시도에서는 누락 또는 중복 가능성이 남는다. 서버에서 정확히 한 번 처리됨을 보장하지 않는다. 사용자/팀 단위 분자도 조사표와 대조한다.
- `safeEventMeta`는 짧은 `stage`/`source` 코드의 잘못된 문자열 자르기를 수정했다. 기존 허용 필드만 유지하며 자유 텍스트 내용을 계측 필드에 넣지 않는다.

## 조사표와 최종 결정

한 행을 하나의 과제 시도 또는 후속 확인으로 기록한다. 원문 대신 다음 열을 쓴다.

`주차 | 참여 코드 | 역할 | 첫/기존 사용자 | 앱 판 | 기기/브라우저 | 과제 종류 | 시작/끝 시각 | 도움 횟수 | 탭 수 | 성공/실패/취소 | 재열람 확인 | 다음 예정일 | 답변 확인 시각 | 앱 밖 재입력 횟수 | 막힌 단계 | 해결 날짜`

**확대:** 저장 신뢰 기준을 모두 지키고, 역할별 첫 성공·4주 반복 사용·주간 코칭 연결 기준을 충족할 때 다음 팀 모집을 제안한다. 이 표본만으로 요금제를 확정하지 않는다.

**수정 후 재검증:** 저장 문제 없이도 한 역할의 첫 성공이나 연결 지표가 낮으면 가장 자주 막힌 단계 하나를 고치고 동일 과제를 다시 본다. 새로운 기능 수를 늘려 실패 원인을 가리지 않는다.

**영향 경로 확대 중지:** 실제 자료 유실·계정 혼입·24시간 초과 미해결 저장이 발생하면 해당 흐름부터 조사하고 수정한다. 기존 참가자 기록을 삭제하거나 테스트 데이터로 덮어 재현하지 않는다.

인터뷰에서는 “무엇에 돈을 낼까요?”보다 “다음 주에도 어떤 일을 여기서 하겠습니까?”, “여전히 다른 도구로 옮기는 일은 무엇입니까?”, “없어지면 가장 곤란한 결과는 무엇입니까?”를 먼저 묻는다. 답변을 지속 사용·효율 향상·지불 의사가 검증된 결과처럼 표현하지 않는다.
