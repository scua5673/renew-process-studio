# 경기 입력 대기·태블릿 종료 후속 조사

담당 제보: `aea93c94-47c5-4df3-8b6e-b430532958ac`, `ac40be30-be3a-4843-8f1a-7b0bcbbf9646`.

## 재현한 경기 입력 차단

그림을 참조로 저장한 서버 일정은 작지만 화면에서 그림을 복원하면 동기화 한도인 350만 자를 넘을 수 있다. 기존 동기화는 그림을 `ps_blob`으로 분리하기 전에 화면 사본의 길이만 검사해 일정을 건너뛰었다. 일정 확인이 끝나지 않아 경기 문서도 매 회차 미뤄졌고 리뷰 입력이 잠겼다.

합성 fixture의 그림 60개 일정을 열고 4개를 추가하면 3,372,683자에서 3,597,464자가 된다. 수정 전 Chromium·WebKit 모두 3회 연속 일정 skipped·경기 deferred를 재현했다. 운영 진단의 일정 skipped·경기 deferred, 작은 서버 일정과 큰 그림 합계가 이 경로와 부합하지만 실제 기기 사본은 읽지 못했으므로 원 제보 전체의 원인이라고 확정하지 않는다.

`sync-size.js`는 기존 thumb/emblem 분리로 한도를 지킬 수 있는 후보만 통과시킨다. 원문 1,200만 자와 그림 하나 200만 자 상한을 지키며, 실제 전송 직전에도 분리된 문서의 기존 한도를 검사한다. 그림 저장이 실패하면 큰 원문을 우회 전송하거나 저장됐다고 확인하지 않는다. 기존 계정·팀·판본·동시 편집 가드는 유지한다.

## 저장 실패 뒤 다시 열 때의 두 번째 차단

WebKit에서 화면 사본 용량 초과와 그림 서비스 403을 겹치면 미전송 일정이 IDB에만 남는다. 새 페이지에는 이전 메모리의 거울 실패 표식이 없어, 새 후보를 IDB에 쓰고 거울 quota 실패까지 확인해도 전송 직전 검사에서 계속 미뤘다. 단위 시험과 실제 WebKit fixture 모두 재현했다.

이번 회차의 정확한 후보 원문에 대한 거울 quota 실패가 확인된 경우만 기존 IDB/CAS 경로로 진행한다. 오래된 실패 표식, 다른 원문, quota가 아닌 실패로 범위를 넓히지 않는다. IDB 읽기 실패·새 IDB/거울 편집·계정/팀 전환은 계속 전송을 막는 회귀 시험으로 검증한다.

## 부팅 중 불필요한 문서 해석

사진을 별도 보관소로 옮기는 시작 처리가 사진 없는 큰 SVG 일정과 텍스트 IDP까지 프레임마다 JSON.parse했다. data:image가 없으면 파싱을 생략하되 JSON Unicode escape가 있으면 기존 파서를 유지한다. 4개 프레임의 360만 자 SVG 일정·100만 자 IDP 합성 시험에서 전체 문서 파싱은 8회에서 0회로 줄었고 원문은 그대로다. 실제 사진·escape된 사진의 이동, 다른 계정·팀과 동시 편집 보호도 검증한다.

이는 불필요한 메모리 할당 감소다. 실제 iPad OS 종료는 재현하지 못했으며 종료 원인 전체가 해결됐다고 판정하지 않는다. 사용자는 실기기 확인이 지금 어렵다고 답했고 가능한 조사와 실사용 배포를 승인했다.

## 검증

- 단위 4,210개·SQL 전체 통과.
- 신규 브라우저 시험은 큰 일정 저장 → 리뷰 입력·서버 저장 → 그림 서비스 403 시 원문 보존 → 다시 열어 복구와 그림 캐시 재사용을 검증한다. 최종 양 엔진·전체 CI·staging 게시 결과는 PR과 배포 기록에 남긴다.
- 실계정 저장소·운영 DB·제보 답변·제보 상태는 수정하지 않는다. 모든 쓰기와 재현은 외부 요청이 차단된 합성 fixture에서만 수행한다.
