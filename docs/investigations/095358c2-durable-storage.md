# 095358c2 · 저장공간 경고와 기기 원본 보존

사용자가 승인한 저장 안정화 후속 작업. 시작 기준은 staging 267db368d00f1e9fd1523f2edb429f4ae6c16868(3.187)이다. 기존 3.184의 원문·작성자·세대 검증과 팀 전환 차단을 보존한다.

## 범위

- 자동 안전 정리와 검증된 저장 재시도를 먼저 처리하고, 지속하는 실제 실패만 크게 알린다.
- 기기 저장과 서버 확인을 구분해 표시하고 같은 실패 안내를 반복하지 않는다.
- 큰 개인 보드 원본과 복구 초안을 IndexedDB에 보관한다. 이전 원문 일치와 복원·전환 검증 전에는 localStorage 원본을 제거하지 않는다.

## 구현

학습 3.189 및 운영 승격 7e1956d를 보존해 통합했고, 후속 판은 3.190이다. 자동 정리는 작성자의 guarded flush와 실제 원문 재확인에 연결한다. 다른 문서의 저장 성공이나 공간 확보만으로 실패를 해제하지 않는다. 기기 사본과 실제 서버 수락을 구분하고, 확인 범위 밖의 자료는 기기 보관으로 표시한다.

개인 보드와 초안은 IDB를 우선하며 exact readback·CAS·소유자·세대·취소 epoch를 확인한다. lifecycle 직전 전체 입력을 보존하고 서로 다른 기존 원문은 별도로 유지한다. 검토에서 own-CAS/LS 후속 편집, 버린 초안의 늦은 재생성, 서로 다른 원본 위로 쓰는 경계를 재현하고 수정했다.

실제 전환 검사에서 정상 source 잠금의 cache 재확인이 generation을 바꿔 전환을 취소하고, 부팅 파생 호출의 seq 변화가 온전한 IDB 초안의 복원 제안을 누락하는 경계를 추가로 찾았다. 의도된 같은 계정·출발 팀 잠금의 읽기 검증과 실제 쓰기 권한을 구분하며, 실제 새 편집·새 저장·버리기·다른 소유자의 오래된 결과는 거부한다. 재확인한 사본이 삭제된 경우 이전 성공 표시도 철회한다. 복원 뒤 늦은 썸네일 작업이 원문을 바꾸는 경합은 최종 sharedReady까지 중첩 동결하고 epoch·lexical 프레임 배열·자기 handle을 검증해 막았다. 원문 비교는 그대로 유지하고 완료 후 정상 썸네일 생성을 재개한다. 화면 높이 측정의 ResizeObserver 피드백도 재현해 프레임당 한 번 측정하고 같은 값을 다시 쓰지 않게 했다.

최초 최종 CI는 9/18로 실패했고 배포하지 않았다. 저장본 페이지의 지연 적용이 실제 새 편집으로 잡혀 복원 제안을 버리는 원인, 보드에서 미팅으로 이동한 뒤 다른 화면의 내용을 보드 원문과 비교해 저장 실패로 보이는 원인을 추가로 재현했다. 저장본의 동기 적용만 기존 capture 잠금 안에서 처리하고, 화면을 떠나기 직전 보드의 정확한 원문·소유자·편집 세대와 실제 저장소의 사본이 일치하는 경우에만 이전 보드 보관을 인정한다. 다른 화면에서는 그 보드를 읽기 검증만 하며, 오래된 병렬 검증이 더 최신 실패나 새 저장을 덮지 못하게 검사 세대를 확인한다. 현재 화면에 실제 실패나 저장 중인 자료가 있으면 이전 보드 보관 표시가 이를 가리지 않는다.

선수단 자료는 실패 뒤 정상 pull로 LS와 IDB에 같은 최신 원문을 저장해도 이전 실패 표시가 남는 경로를 고쳤다. 실패했던 정확한 키·원문·소유자와 두 저장소의 실제 사본, 최신 실패 번호가 모두 같은 경우에만 회복을 인정한다. 다른 원문·다른 팀·늦은 성공으로 실패 표시를 지우지 않는다. 표시 전용 fixture는 실제 저장 상태를 검사하는 fixture와 분리해 기대 상태를 맞췄으며, 실제 저장 실패와 전환 장벽 검사는 유지했다.

후속 CI40377588541도 14/18로 실패해 배포하지 않았다. 다른 화면의 개인 보드 저장을 막는 guard가 미팅의 기존 슬라이드 미리보기 갱신도 중단해 현재 첫 슬라이드에만 선수 이름이 보관되지 않는 회귀를 원본 시험으로 재현했다. 미팅 모드에서는 기존 preview 예약만 수행하고, 개인 보드의 원문 캡처·편집 세대·dirty·초안 경로는 계속 차단한다. 해당 fixture가 요청한 WebKit 대신 desktop Chromium을 열던 설정도 바로잡아 실제 엔진을 확인한다. 별도 Chrome 경기 일정 정착 실패는 원본 CI에 최종 원문과 pending 값이 없어 원인 미확정이며, 로컬 정상 1회만으로 해결됐다고 표시하지 않는다. 기존 단정과 대기 한도를 유지하고 합성 저장소·서버·outbox 상세 진단을 남긴다.

일정 IDB 응답 하나를 보류한 실험에서는 초기 정체가 재현되지 않았고 root는 서버 원문 일치·pending 0으로 자연 회복했다. 시험이 실제 scout 저장 완료 전에 다음 서버 편집을 주입한 준비 조건의 빈틈은 확인했다. 기존 원문·경기 번호·root pending 조건에 실제 scout의 저장 완료·대기 없음·동일 원문 조건을 추가했고, 현재 제품의 Chrome 1회에서 전체 흐름을 통과했다. 늦은 옛 원문 거절은 최신 원문 보호 조건을 유지하며, 이것을 원래 CI 정체의 해결 증거로 사용하지 않는다.

WebKit 선수단 시험의 두 비동기 대기는 사용 중인 Playwright 구현이 Promise 자체를 참으로 받아 실제 false 결과를 기다리지 않는 경계를 재현했다. 실제 IDB 조회가 끝난 뒤 같은 시점의 준비 상태·대기열·편집 화면·원문을 검사한 객체를 제한 시간 내 await해서 기록하도록 고쳤다. 실제 다음 동기화 회차의 busy/ready false에서 검증된 ready true 사본으로 진행하는 것을 상태 모킹 없이 확인했다. 기존 두 번의 실패·원문 보존·재시도 단정은 유지한다.

CI40387062013은 16/18로 실패했고 배포하지 않았다. 유일한 WebKit 큰 일정·경기 리뷰 실패는 최초 입력 뒤의 실제 사본·대기열 기록이 없어 원인 미확정이다. 같은 소스의 일반 진단 1회와 다음 실제 회차 진단 1회에서는 전체 흐름이 통과했으므로 이를 해결 증거로 사용하지 않는다.

별도의 실제 두 번째 입력 실험에서는 첫 리뷰 동기화가 MATCH를 defer한 직후 문서 준비표는 대기인데 textarea는 편집 가능한 상태를 관측했다. 이때 친 글은 기존 typed 메모리에만 남고 본문 입력 처리기는 거절했다. 입력 2ms 뒤 실제 psHasPending은 false, psFlushPendingReady는 true였으며 LS·IDB에는 첫 값만 있어 이동 안전 판정의 결함을 확정했다. 실제 이동이나 유실은 실행하지 않았고 자연 회복 뒤에는 두 번째 값도 저장됐다.

typed 입력을 기존 전환·새 판 적용 검사와 저장 큐에 연결한다. 준비가 돌아오면 현재 소유자·경기·담당자 권한과 필드 기준값을 다시 확인하고, 준비가 안 됐으면 match_input_pending으로 거부하며 현재 입력의 기존 저장 표시를 대기로 바꾼다. 미저장 입력은 60초 만료로 조용히 지우지 않는다. 소유자를 확인할 수 없는 동안은 완료로 판정하지 않으며, 이전·미확인 작성자의 입력을 새 계정 화면에 복원하지 않는다. 큰 일정 시험은 기존 6회·250ms 한도와 이미지·403·재접속 단정을 유지하고, 예상한 입력 대기만 실제 다음 회차 후 다시 flush한다. 다른 저장 오류는 그대로 실패하며 마지막 메모리·LS·IDB의 정확한 리뷰 값도 검사한다. 이 수정은 기기 전용 영속 초안을 추가하지 않으며 강제 종료 복구를 보장하지 않는다.

수정 후 표시 검사는 Chromium에서 실패해 배포를 멈췄다. 실제 호출 추적에서 새 입력의 대기 표시 뒤 이전에 수용한 값의 320ms 저장과 완료 콜백이 정상 실행되어 같은 소유자·경기에서 ‘방금 자동 저장됨’으로 덮는 원인을 확인했다. 현재 모델과 다른 최신 미반영 입력이 있는 동안 비실패 표시에 대기를 우선하며, 실제 실패와 이미 수용된 입력의 표시는 보존한다. 새 입력 검사가 기존 320ms 저장 간격을 바꾸거나 실제 I/O 실패를 짧은 간격으로 반복하지 않는 행동도 고정했다. 실패 후 같은 값 재표시는 재시도를 재개하지 않고, 명시 재시도나 같은 작성자의 새 의미 입력만 기존 권한·기준값 검사 뒤 재시도한다.

## 검증

H5 CI40397512080은 16/18로 실패했다. 이전 경기 입력 두 엔진은 통과했으나 WebKit 긴 이름 시험의 393px 명시 저장이 개인 head 보호 오류로 거절됐다. 같은 원본 4폭을 startup부터 투명 계측한 단 한 번의 로컬 진단은 21회 head 저장·재접속 모두 통과했으므로 CI의 정확한 throw 분기는 아직 미확정이다. 추가 반복으로 통과를 얻지 않았고, 원래 단정과 대기 한도는 유지한 채 이후 실패에 원래 stack·세대·seq·token을 남긴다.

별도 제한된 실제 함수 재현에서는 첫 개인 head의 조회·CAS·정확한 readback 각각을 기다리는 동안 같은 화면의 자동 새로고침 재시도가 새 attempt 레코드를 먼저 만들어 앞 명시 저장을 무효화했다. 서버에는 정상 저장됐는데 명시 결과는 false이고 기기 저장 실패 안내가 나왔다. send가 현재 소유자·세대의 local queue가 안정될 때까지 기다린 뒤 최신 레코드를 읽고, 기존 attempt도 실제 head에 다시 보관·검증한 후 서버에 보내도록 고쳤다. 큐의 과거 실패를 성공 receipt로 인정하지 않으며 현재 다른 원본·소유자 변경·실제 저장소 실패 검사는 유지한다. 이것을 원시 stack이 없는 H5 CI 실패의 확정 원인으로 표시하지 않는다.
