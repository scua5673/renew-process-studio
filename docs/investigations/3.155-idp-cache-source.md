# 선수 IDP 읽기 캐시의 반복 저장 확인 실패

진단 식별자: `idp_other_cache_verify` / `kv-write-source-mismatch`.
2026-10-24 00:25~01:44 KST, 3.153 desktop에서 약5분 간격 반복. 운영 자료는 읽거나 수정하지 않았다.

동일 3.154 소스의 합성 fixture에서 다른 선수의 private IDP에 과거 IndexedDB 사본이 있으면 `kvWrite`가 IDB 경로를 선택하지만, IDP 읽기와 업로드 기준은 localStorage다. 두 사본이 같을 때도 비동기 IDB 저장 완료 전에 localStorage를 검사해 최초 실패한다. 두 사본이 다르면 CAS 실패와 미처리 promise 거부가 반복되고 캐시가 갱신되지 않는다. 서버 원문은 유지된다. 실제 계정의 두 사본을 확인한 것은 아니므로 운영 진단의 원인을 단정하지 않는다.

수정 방향: 기존 `currentValueForKey`와 같은 IDP 원문 기준을 쓰기에도 적용한다. IDP private/public의 localStorage CAS·소유자 확인·오류 처리를 유지하며, 우연히 남은 IDB 사본을 쓰기 기준으로 삼지 않는다. stale IDB 원문을 지우거나 서버로 올리지 않는다. 합성 회귀·관련 브라우저·전체 CI 및 staging 게시 검증 뒤 기존 절차로 승격한다.

## CI의 보드 새로고침 검사 보강

## 복원 실패의 재현 원인과 수정

같은 합성 fixture에서 첫 기기로 개인 보드를 저장한 뒤, 저장소가 빈393px WebKit 기기의 개인보드 GET을6.5초 붙잡았다. `ready/done/loaded/current=true`, `base=false`, `edit=15`, `dirty=true`, `userTouched=false`, `players=[]`를 재현했다. dirty 전환 stack은 `app.html` 모바일 도크의 첫 부팅 기본값 클릭 → `setTokShape` → `boardSaveLive`였다. 서버 조회 중 부팅 코드가 편집 순번을 올려, 복원 보호가 기존 서버 문서를 ‘새 편집 위에 덮으면 안 됨’으로 보류했다. 빈 서버였던 첫 폭에서는 creation preimage를 만들 수 있어 통과하고, 서버에 저장본이 생긴 두 번째 폭에서는 기준이 끝내 준비되지 않는 이유와 일치한다.

모바일 기본값 처리는 초기 복원 완료 뒤 수행한다. 저장된 보드나 실제 사용자 편집이 있으면 기존 설정을 우선하고, 빈 보드에 기본값을 적용하는 동기 클릭은 capture lock 안에서 수행해 편집으로 표시하지 않는다. 복원의 CAS·세대·소유자·사용자 편집 보호는 완화하지 않았다. 동일 지연 조건에서 서버 선수701·설정이 복원되고 exact 저장이 가능한 것을 양쪽 엔진 네 폭으로 확인한다. 기존 이름 검사도 그대로 유지한다. 실제 iPadOS 프로세스 종료를 해결했다고 주장하지 않는다.
