# 3.152 저장·복구 및 팀 전환 안정화

관련 제보: cae91d4f (팀 전환), aea93c94 (저장 확인/경기 입력), ac40be30 (iPad 종료).

사용자가 권장 순서의 안정화와 검증 후 실사용 배포를 승인했다.

- 먼저 전환의 마지막 로컬 저장 확인 이후 새 대기가 생기는 경우를 합성 fixture로 조사한다.
- 저장 실패와 서버 미확인을 성공으로 표시하거나 원문을 지우지 않는다.
- 보관함/백업의 큰 데이터 처리 비용을 측정하고 재현된 부담만 줄인다.
- iPadOS 실제 종료와 원래 제보의 동일 원인은 별도 확인이 필요하다. Chromium/WebKit 합성 통과를 실제 iPad 해결로 기록하지 않는다.
- 운영 데이터/실계정 저장소/제보 상태 변경 없이 진행한다.

조사 및 검증 결과는 구현 후 이 문서에 추가한다.

## 재현 및 수정

1. 서버 회차와 대기 확인 뒤 마지막 프레임 저장/키 목록 읽기/보드 flush에서 새 대기가 생기면 기존 전환은 원본을 지웠다. 지우기 직전 다시 대기 목록을 확인하고, 새 변경이 있으면 프레임과 원문을 유지하며 전환을 취소한다. 다음 시도는 새 원문을 원래 팀에 확정한 뒤 진행한다. 명시적으로 저장을 생략하는 기존 팀 나가기 경로는 유지한다.
2. IndexedDB의 대기 목록을 읽지 못하면 기존 outboxRead가 비어 있는 localStorage 사본으로 대체했다. 전환/로그아웃의 파괴적 정리 판정만 엄격한 읽기를 사용한다. 읽기 실패를 대기 0건으로 간주하지 않는다. 일반 상태 표시의 기존 fallback은 유지한다.
3. 보관함 IDB 읽기가 끝난 뒤 revision을 읽어 옛 본문에 새 revision이 붙을 수 있었다. 읽기 전 revision을 잡고, 결과 해석 전에 다시 비교한다. 달라졌으면 파싱/서버 쓰기/확정을 중단하고 다음 회차에서 새 원문을 읽는다.

## 검증

- 수정 전 합성 단위 검사에서 위 세 경로 실패, 수정 후 단위 4,219개와 격리 SQL 전체 통과.
- Chromium/WebKit: 대기 목록 읽기 실패 시 원문 유지, 마지막 저장 후 전환 취소, 재시도 시 원래 팀 서버 반영·대상 팀 분리 통과.
- Chromium/WebKit: 보관함 읽기 중 revision 변경 차단, 새 로컬 원문 보존, 다음 회차 실제 새 본문 전송 통과.
- 큰 보관함 부팅/아이패드 크기 검증 및 CI·staging 결과는 배포 기록에 이어 적는다.
- 실제 iPadOS 기기는 현재 접근할 수 없다. 합성 WebKit 결과를 iPadOS 종료 해결로 세지 않는다.
- 운영 DB·실계정 저장소·제보 답변/닫기 변경 없음.
