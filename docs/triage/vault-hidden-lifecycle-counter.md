# 보관함 숨김 회귀 시험의 읽기 집계 범위

staging `b176ca389d4e0aa9f1f68fdce97f450a843abaf1`의 CI `40156867895` WebKit entry는 숨김 방지 동작을 통과했지만, 다시 보인 뒤의 전체 `libGet` 합계가 예상보다 하나 많아 실패했다. 동일 소스의 로컬 WebKit 계측으로 1280px에서 같은 실패를 재현했다.

실제 순서: 2447ms에 프레임을 다시 보임 → `board-vault-lazy.js`의 `flush`가 2455ms에 그리기를 요청 → 2456ms에 첫 읽기 시작 → 2474ms에 별도의 `ps-auth-state` 메시지가 `psVaultAuthChanged`를 호출 → 이미 시작한 읽기에는 합류하지 않고 새 읽기를 예약 → 2510ms에 두 번째 읽기 시작. 두 읽기 모두 프레임이 보일 때 시작했다. 숨은 큐의 읽기 0회와 숨은 DOM 유지 조건은 통과했다. 호출 스택과 시각 증거는 `/tmp/ps3170-evidence/vault-extra-read-proven.json`에 남겼다.

`psVaultRenderRead`는 아직 시작하지 않았고 쓰기 차례가 끼지 않은 요청만 합친다. 시작한 읽기를 새 요청이나 쓰기용 읽기와 공유하면 최신 값과 저장 순서가 깨질 수 있다. 따라서 자동 재진입 뒤의 모든 읽기를 항상 1회로 제한한 시험 계약이 잘못됐다. 제품 코드는 변경하지 않는다.

시험은 숨은 큐의 읽기 0회, 진행 중 읽기의 숨은 DOM 반영 금지, 재진입 뒤 실제 새 읽기 완료와 자동 렌더, 106개 원본 ID와 서버 원문 보존을 계속 검사한다. 정확히 1회 읽는 조건은 시험이 동기적으로 요청한 세 렌더의 큐 작업에 범위를 붙여 실제 `libGet` 호출을 세어 검증한다. 별도 인증 알림의 정당한 새 읽기는 이 세 요청의 읽기로 세지 않는다. 허용 횟수를 2회나 3회로 늘리는 수정이 아니다.
