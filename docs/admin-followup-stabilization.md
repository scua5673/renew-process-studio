## 실제 변경 전후

### 저장 응답 검증

기존에는 id·사용자/팀·증가한 version만 맞으면 메모/담당/상태가 다른 응답도 저장 성공으로 표시했다. 합성 회귀의 원 실패는 `{note: 'Old memo'}` 응답에서 `true !== false`였다.

수정 후 SQL의 CAS 계약대로 정확히 다음 version과 전송한 사용자·팀·분류·상태·메모·담당자·배포 버전·동일 시점의 다음 확인일을 모두 확인한다. 응답이 다르면 id/version을 채택하지 않고 입력을 보존한다. 자동 재전송을 막고 기존 새로고침/기록 비교 경로를 사용한다. 실제 저장 성공 후에는 운영 홈의 후속 확인 목록을 다시 읽는다. 읽기 실패가 성공한 쓰기를 실패로 바꾸지는 않는다.

### 기존 후속관리로 연결

제보 내용의 **후속 확인 열기**는 확인된 제보자 계정만 기존 사용자 상세에 연결한다. 계정이 없는 옛 응답에서는 추측하지 않는다. 제보 본문/진단을 복사하거나 고객에게 답하지 않는다.

새 기록 초안은 기존 `note`에 제보 참조와 다음 항목을 채운다: 분류, 현재 단계, 재현, 수정/검증 근거, 실제 게시 결과, 사용자 기기/적용, 해결 확인, 기존 자료 복구, 종료 사유, 다음 행동. 배포 버전은 비워 두고 해결·복구는 미확인으로 시작한다. 같은 참조의 기록이 있으면 그 기록을 연다(이미 입력 중이면 입력을 덮지 않는다). **열기 자체는 쓰기가 아니다.**

기존 상태 값과 기록은 그대로다. 표시 문구는 확인 중/배포 후 사용자 확인 대기/확인 완료(해결 근거 별도)/종료(해결 여부 별도)로 뜻을 분명히 한다. 과거 verified/closed를 일괄 해결·재개방하지 않는다. 증거의 진위를 자동 판정하는 기능은 추가하지 않았다.

## 기존 도구에서 운영하는 순서

1. 제보를 읽고 후속 확인을 연다. 동일 제보의 기존 기록을 먼저 사용한다. 다른 제보와 연결할 때는 원래 참조와 각 사용자 근거를 메모에 함께 유지한다.
2. 담당자 **한 명**과 다음 확인일을 기존 필드에 적는다. 분류는 메모에서 하나만 남긴다. 정보 부족은 필요한 증상/기기/순서를 적고, 기능 요청은 주간 선택 대상으로 둔다.
3. 현재 단계를 하나로 적고 재현 자료 → PR → 원 실패 및 수정 후 검사 근거를 순서대로 남긴다. 기술 검증만 끝났으면 사용자 해결 확인으로 옮기지 않는다.
4. 실제 게시가 확인되면 배포 버전과 게시 근거를 적고 `deployed`에 둔다. 같은 기기에서 새 판 적용 → 원 행동 성공을 확인하기 전에는 해결 미확인이다.
5. 사용자가 원 흐름을 완료한 근거가 있으면 확인 완료로 기록한다. 기존 자료 복구는 **복구 확인/미확인/복구 불가/해당 없음과 사유**를 별도로 적는다. 새 저장 성공이 옛 자료 복구를 뜻하지 않는다.
6. 무응답이면 `closed`와 메모의 **미확인 종료·마지막 시도·다시 확인할 조건**을 함께 남긴다. 제보 접수 상태를 바꾸는 일은 기존 승인 절차를 따른다. 이 작업은 어떤 운영 기록도 생성/수정하지 않았다.

## 재현·검증

### 관리자 원 수정

원 코드에서 잘못된 응답의 성공 표시를 재현한 뒤 수정했다. 기존 95ac88c1에서는 Node 22 단위 5,446개·전체 SQL, Chromium 보조 실행 파일의 관리자 흐름을 통과했고, 이후 공식 CI의 Chromium/WebKit 18묶음·regression·release-gate 20개 모두 성공했다. 첫 단위 실행의 기존 함수명/자산 판 고정 실패 2개도 숨기지 않았다. 함수 진입점을 보존하고 자산 검사는 일반 cache pin 검사로 바꿨다.

잘못된 메모/담당/분류/상태/배포 버전/확인일/version, 시간대가 다른 동일 시점, 전송 중 입력, 늦은 조회·다른 계정·409·응답 불명·권한 실패를 검사한다. 기존 닫힘 기록은 그대로다.

### 최신 통합판 검증

## 통합·되돌리기

753의 원 head와 최신 staging을 부모로 하는 병합으로 이력을 유지한다. 로컬 3-way 병합 계산은 충돌 표시 없이 완료됐다. GitHub의 이전 mergeable 표시만 믿지 않고 실제 병합과 원문 비교를 수행했다. 강제 push·rebase·다른 PR/브랜치 수정은 하지 않는다.

선수 저장·메뉴·훈련 도구 코드는 최신 staging의 구현과 시험을 그대로 가져온다. 753이 추가하는 제품 변경은 관리자 후속 연결·정확한 저장 응답 확인뿐이다. app/sw는 배포 번호만 갱신한다. 미병합 #755가 사용하는 3.248의 번호/구현을 이 가지에서 덮지 않는다. #755가 staging에 합쳐지면 그 통합 결과를 기준으로 다시 확인한다.

새 head의 필수 CI를 끝까지 확인한 뒤 검토 준비를 완료한다. 운영 승격/실계정 기기 확인/고객 자료 복구 완료는 이 PR의 자동 검사와 별도이며, 사용자 확인 없이 병합·승격·운영 배포하지 않는다.

원복은 **staging 대비 753이 추가한 관리자 변경**을 되돌리는 PR로 한다. 최신 staging을 포함한 병합 커밋을 통째로 역병합해 선수 복구·메뉴 수정을 되돌리지 않는다. 필요한 배포 번호는 현재 판보다 높은 번호로 다시 맞추고 기존 검사를 수행한다. DB/고객 자료를 되돌릴 필요가 없고 새 메모도 옛 화면에서 그대로 읽힌다. 게시 후 원복은 기존 Netlify 배포 복원 절차와 공통 판 정책을 따른다.
